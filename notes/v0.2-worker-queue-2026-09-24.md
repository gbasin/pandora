# Worker queue and learned size classes, 2026-09-24

On 2026-09-24 three remote jobs (`build`, `code`, `full`, all `size = "large"`,
8192 MiB reservations) were refused with `admission-refused: memory`. Other
sessions' runs held 7.8 GiB of the worker's 14 GiB budget. A plain remote run
was admitted or refused at submit. Only the local lane and sharded fan-outs
waited. Large jobs never fall back, so a busy worker meant exit 70 for every
large job.

Branch `feat/worker-queue`. Nothing here ran on the live worker. The unit
tests use the existing fakes only; see "Unverified".

## Rulings (Gary, 2026-09-24)

1. **A full worker queues; it does not refuse.** The engine keeps a `queued`
   row and admits in arrival order. There is one queue for everything, with no
   priority and no per-client share yet.
2. **The wait is bounded by the job's learned duration**:
   `max(120 s, min(1800 s, 3 x p50))` of the last runs of that (repo, job).
   With no history, 600 s. Past the bound the run is `infra_failed`, cause
   `queue-timeout`, exit 70, and never falls back. There is no config key.
3. **Small and medium jobs no longer fall back on a full worker.** They queue
   like everything else. The local lane stays the fallback for `worker-down`,
   `worker-unreachable`, `snapshot-failed` and `transfer-failed` (before
   `accepted`). `admission-refused` and `queue-timeout` are non-fallback causes,
   exit 70.
4. **Sizes are learned both ways.** The declared `size` is the starting class.
   After 3 clean samples, the class used for reservation and ceiling is what
   `p95 x 1.25` justifies, up or down, from small to xlarge. An `oom` resets
   it to the declared class.

## Who waits where

The engine waits, not the Mac. `submit` answers `state: queued` and spawns a
detached **waiter** (`pandora/engine/waitlist.py`, verb `wait`) for the row.
The waiter polls every 2 s under the admission gate. On each poll it touches
the row as a heartbeat. When the scheduler admits the row, the waiter spawns
the ordinary supervisor and exits. No supervisor exists until admission, so
`supervisor_pid` still means "the command may be running". The waiter's pid is
a separate column, `waiter_pid`.

Why the engine and not a daemon poll: the queued row lives in the worker's
ledger. A Mac-side daemon that restarts, or a client that disappears, changes
nothing about the queue or the deadline. `reconcile` after an engine restart
starts a new waiter for a queued row whose waiter died. The row keeps its
`queued_at`, so it keeps its place and its deadline.

The daemon watches. After `submit` answers `queued`, `Daemon.wait_in_worker_queue`
polls `status` every 2 s. The engine's `status` of a queued row carries its
`queue` place. The daemon's heartbeat (`working` every 5 s) continues through
the wait, so the shim's 120 s handshake silence rule is never tripped. The
caller hears a pre-accept `notice` frame, the existing frame kind, with a
`queued` object beside the sentence: once, then at most every 60 s. This is the
shard queue's rhythm from `fanout.admit_and_spawn`. `accepted` is sent only
after the engine admits the run, so the before/after-`accepted` split of the
fallback policy is unchanged. The queue wait is not a fallback cause.

### Arrival order

`Scheduler.queue()` is every row in state `queued` with a `queued_at`, not a
fan-out parent, and touched within `QUEUE_STALE` (30 s). It is ordered by
`queued_at`. `Scheduler.admit` refuses with reason `queue` while any older row
is waiting, even if this row would fit. A large row at the head therefore
blocks smaller rows behind it; that is the ruling. Shards join the same line:
`admit_and_spawn` stamps `queued_at` on its first refusal and re-stamps it on
each pass. A shard the parent has not tried to dispatch yet has no `queued_at`
and holds no place. A row whose waiter died drops out of the queue after 30 s
instead of blocking its head forever.

### The bound, as coded

`waitlist.bound`: the median of `history.samples(key='run')`, which is
`finished - admitted_at` (or `created` for rows from before this change) over
the last 5 verdicts (`passed` or `command_failed`) of the same (repo, job,
role). Fewer than 3 samples gives 600 s. Otherwise
`max(120, min(1800, 3 x median))`. Measured from admission so that time earlier
runs spent queued does not stretch the next run's patience. Fixed at submit as
`queue_deadline` (wall clock).

## Behaviour table

| Worker state at submit | Engine answer | Client |
|---|---|---|
| fits | `admitted`; supervisor spawned | `accepted` |
| memory is short, or older rows are waiting | `ok`, `state: queued`, `queued: {position, ahead, running, eta_seconds, bound_seconds}`; waiter spawned | notice lines, then `accepted` on admission |
| every slot taken (`max_running`) | `admission-refused`, reason `slots` | refuse, 70, no fallback |
| reservation larger than the whole budget | `admission-refused`, reason `memory`, `never: true` | refuse, 70, no fallback |
| pool below the disk floor | `disk-floor` (unchanged) | as before (`engine-error` policy) |

| While queued | Result |
|---|---|
| admitted | `accepted`; the run streams as any other; `durations.queue` in the result |
| the bound passes | `infra_failed`, `queue-timeout`, `cli_exit` 70; the daemon row is `infra_failed` with `refusal.cause = queue-timeout` and the engine's result; exit 70; not retried |
| `pandora cancel`, or Ctrl-C | the engine withdraws the row (`cancelled`, `evidence.withdrawn`), exit 130 |
| the caller leaves | withdrawn; the daemon row is `withdrawn` |
| a drained daemon restart | `cancel --queued-only`: withdrawn if still queued, and the caller gets `draining` and submits again at the back of the queue. If admission won the race, the run is followed as accepted. |
| the daemon crashes | the row stays queued on the worker; the next daemon's `settle_unaccepted` looks it up (`spawned` is true for a waiting row) and follows it |
| the worker stops answering `status` 6 times in a row | `execution-uncertain`, 70; never a fallback |

`pandora run --detach` returns at `accepted`, so a detached submission now
waits through the worker queue before it prints the run id. The local lane
already behaved this way.

A drained restart loses the queue position. The alternative was to block the
drain for up to 30 minutes on a pre-accept row. That matches the local lane,
where a drain also withdraws queued runs.

## Learned size classes, as coded

`Scheduler.learn`, at the end of every supervised run, under the gate:

* `oom`: the peak is stored as before and never learned from. The class is
  reset to the declared one (`Store.set_class(..., declared=...)`).
* `passed` or `command_failed`: when there are at least 3 clean peaks recorded
  after the job's last `oom` (`Store.clean_since_oom`), the class becomes
  `admission.classify(peaks, learned=True)`. That is the smallest class whose
  ceiling is at least `p95 x 1.25`, and xlarge above that.
* `timed_out`, `cancelled`, `infra_failed`: nothing about size.

Counting only peaks after the last `oom` prevents a loop. The peaks that chose a
class that was then killed would otherwise choose it again on the next clean
run. `Store.size_class` ignores a learned class whose `declared` differs from
the job's current declaration, so editing `size` in `pandora.toml` restarts
learning from the new value.

The class sets both the reservation (`admission.reserve` clamps to the class
ceiling) and the ceiling. `runner.supervise` builds `Limits` from the row's
`ceiling_mib`, which admission writes from the learned class. When `learn`
changes the class, the run's log gets
`pandora: size for <job>: <old> -> <new> (p95 <n> MiB over <k> runs)` before
the row is marked finished, so the client still streams it. An `oom` reset says
`(an oom resets it to the declared class)` instead. The line is on the run that
taught the change; that run already had its class. The result records
`size_declared`, `size_used` and `learned.size_change`.

The local lane's own `Admission` store is untouched: it still records the
declared class and does not learn it.

## Wire and engine version

`ENGINE_VERSION` 3 -> 4 (`pandora/engine/service.py`).

* `submit` may answer `{ok: true, state: "queued", queued: {...}, waiter_pid}`.
  A duplicate submit of a queued row answers `state: queued` with `queued`.
* `status` of a queued row carries `queue: {position, ahead, running,
  eta_seconds, waited_seconds, bound_seconds, deadline}`.
* `cancel` of a queued row answers `withdrawn: true`. `cancel --queued-only`
  withdraws only a queued row, and otherwise answers `withdrawn: false`
  without asking the run to stop.
* `lookup` answers `spawned: true` for a row a waiter holds, plus
  `queued: true`.
* New internal verb `wait --run <id>`.
* Results: `size_declared`, `size_used`, `durations.queue`,
  `learned.size_change`; `evidence.cause = "queue-timeout"` with
  `evidence.queue`.
* Ledger columns (added by the ALTER-TABLE migration): `queued_at`,
  `queue_deadline`, `admitted_at`, `waiter_pid`, `size_declared`. The peaks
  store's `classes` table gains `declared`.
* Client frames: no new frame kind. The queue lines are `notice` frames with
  an extra `queued` object. The row in `meta.json` gains `queue`, and `phase`
  is `queued` while the run waits. `ps` shows `queued #N`.

An older daemon talking to a v4 engine reads `ok: true` as admitted and sends
`accepted` early. The run still waits on the worker and then runs. Only the
pre-accept guarantee and the queue lines are lost. A v4 daemon talking to a v3
engine never sees `queued`.

## Fallback

`fallback.NEVER_LOCAL = ('admission-refused', 'queue-timeout')`: `decide`
refuses these at any size and whatever the job declares, with the next step
("Retry, or run it in the local queue with PANDORA_WHERE=local" when the job
can run there). They stay in `CAUSES` and `loader.FAULTS`, so a `pandora.toml`
that names them still loads.

## Stats

`pandora stats` reports `worker_queue: {wait_seconds: {n, p50, p95},
timeouts}`. Waits come from the engine's `durations.queue` on remote results.
Timeouts come from `evidence.cause` or the row's `refusal.cause`. The
pre-accept wait line now says it includes any queue.

## Tests

`pandora/tests/test_worker_queue.py` (29) covers the engine: queueing on memory,
waiter admission, arrival order and head-of-line blocking, the stale-row rule,
slots and never-fits refusals, the disk floor, `status`, duplicate submit,
`lookup`, the supervisor guard, withdraw by `cancel` and by the waiter, the
bound formula and its clamps, `queue-timeout`, `reconcile` restarting a waiter,
shards in the same line, and the class learning rules end to end through
`supervise`. `pandora/tests/test_daemon_queue.py` (11) covers the daemon: notice
frames and their order before `accepted`, the repeat line, the heartbeat under
the wait, `ps`, timeout (exit 70, no fallback, counted in stats), cancel, the
caller leaving, a drain, a silent worker, and lost-reply recovery. Existing
fallback and multi-client tests were updated where the ruling changed the
expected answer.
