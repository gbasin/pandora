# v0.2 direction, 2026-09-21

This note consolidates one review session: the [readiness triage](eichler-readiness-2026-09-21.md),
five proofs of concept, one external critique, and the owner's decisions. The
POC branches are local and unpushed; each carries its own dated note with
commands and evidence. Nothing here changes v0.1.1 behaviour.

| Branch | Content |
|---|---|
| `poc/repo-config` | Repo-owned `pandora.toml`, generic classifier, 77-case parity with `commands.py` |
| `poc/ci-import` | Importing facts from the target's `ci.yml`; drift lint; review fixes |
| `experiment/codex-sandbox` | What a Codex shell tool can do under each sandbox mode |
| `poc/docker-proxy` | Per-run Docker API proxy; Eichler journey runner |
| `spike/linux-proxy` | Proxy verified on the Linux worker |
| `spike/firecracker` | MicroVM per run, and an Incus system-container trial |
| Eichler `agent/shared-surface-runner`, `agent/journey-runner-proxy` | Shared runners called by CI, local validation and Pandora |

## Decisions

1. **Freeze v0.1.1; build v0.2 clean.** No pilot on the welded adapters.
2. **Pandora is repo-agnostic.** Command knowledge lives in the target
   repository as runner scripts that its CI, its local validation and Pandora
   all call. `pandora.toml` states only what CI has no notion of: which argv
   forms Pandora claims, a size class, the shard environment mapping, output
   and write-back paths, fallback policy. The flag/template mini-language from
   the first draft is dropped; unknown flags pass through to the runner.
3. **Two-tier contract.** Tier 1: run the argv with
   `PANDORA_SHARD_INDEX/TOTAL` (or an argv template). Tier 2 adds an optional
   `plan` command emitting a JSON inventory and a report Pandora checks
   against it, the same role as Bazel's shard status file. Build-once is
   "plan may produce outputs shards mount".
4. **`ci.yml` is linted, not read.** Import by reference worked on Eichler's
   real workflow and found two errors in the hand-written config, but it saves
   about 45 lines at the price of parsing a file Pandora's owner does not
   control on every agent command. The lint raises the same drift as a CI
   failure.
5. **Eichler changes wait for the journeys runner**, then land as one PR. The
   surface runner proved the hypothesis: 302 and 433 tests partition exactly,
   focused `--grep` inventory equals execution, and `vite build`/`playwright
   test` no longer appear in `ci.yml`, `plan.mjs` or app scripts.
6. **Scheduling: admit on memory, CPU soft.** cgroup weight rather than quota;
   runners receive a CPU hint and size their own workers. Reservations are
   learned from observed peak usage with the size class as the ceiling.
7. **Tenancy: one worker (or pool) per trust domain.** Runs are isolated from
   each other for correctness and capacity; the shared kernel is trusted.
   Whether a VM tier is ever needed is open; the executor interface stays
   narrow enough to add one.
8. **Secrets and egress: none and open.** The classifier claims only commands
   that need no credentials; everything needing them already stays local.
   Secret-looking environment names are dropped with a notice. A
   credential-injecting proxy is the reserved design if authenticated work is
   ever routed.
9. **Warm disk only.** No pool of booted instances, no snapshot restore yet.
10. **Worker unreachable or queue timeout falls back to local**, only before
    acceptance (see Fallback below).

## Executor: measured on the 4 vCPU / 15 GiB worker

All three ran Eichler journey `S0-01` end to end with Eichler's own Compose
stack. The box was shared between spikes, so treat times as ±20%.

| | Host dockerd + API proxy | Firecracker per run | Incus system container |
|---|---|---|---|
| `S0-01` wall | 57.3 s | 141.4 s | 62.7 s |
| Per-run start | container start | 0.54 s restore (stack already up) | 0.35 s clone, dockerd ready 0.21 s |
| Eichler change | 8 lines (`STACK_CALLER_ON_NETWORK`) | none | none |
| Pandora code | ~1,200 lines proxy + sweep | image pipeline, guest agent, tap/NAT | thin driver over the Incus API |
| Fixed ports, `localhost` | via network attach | native | native |
| Accounting | one systemd slice per run | host RSS overstates (1.1 GiB demand → 3.1 GiB RSS, 6 GiB reserved) | one cgroup; `memory.peak` 2,896 MiB |
| Soft CPU / memory | slice `CPUWeight`, `MemoryMax` verified | vCPU threads weightable; memory is a lazily committed ceiling | `limits.cpu.allowance` → `cpu.weight`; `enforce=soft/hard` → `memory.high`/`memory.max` |
| Kill mid-run | label sweep, receipt clean | kill VM, 4 host objects to reap | delete, 1.1 s, nothing left |
| Needs KVM | no | yes | no |

**Direction: Incus system containers behind an executor interface**
(`prepare / clone / execute / usage / collect / destroy`). A run is a small
machine that owns a private dockerd, so the repository's stack boots
unmodified, fixed ports never collide, cleanup is deleting the instance, and
accounting is one cgroup. Copy-on-write clones of a golden instance per (repo,
install fingerprint) carry dependencies and pre-pulled service images. The
same API launches QEMU VMs (18.8 s boot measured) if a hardware tier is
wanted.

The proxy is a proven fallback and its `sweep`/`usage` primitives remain
useful. Firecracker is kept as a documented tier-2 option; its snapshot
restore of a booted stack (0.54 s) is the one capability containers cannot
match.

One run's memory is about 1.9 GiB toolchain and 0.09 GiB services. v0.1.1
reserved 4,864 MiB for the same journey.

### Open executor risks

- Incus `memory.max` livelocked in reclaim instead of OOM-killing (349,230
  events, `oom_kill 0`). Contained to the instance, but a run needs a
  watchdog or a different limit arrangement before hard ceilings are trusted.
- Nested Docker in unprivileged containers has broken on host updates before
  (runc's CVE-2025-52881 fix under AppArmor, until Incus 6.19). The worker
  needs a pinned image and a canary; the upkeep policy is undecided.
- Not run: more than two concurrent runs, balloon, jailer, arm64, Sysbox,
  Kata, gVisor. Firecracker output read-back came back empty, undiagnosed.

## Client

A launchd client daemon plus a thin shim in the first directory of the login
PATH (`~/.local/bin` on the owner's Mac) is the candidate. Measured: under
Codex's default read-only sandbox neither a daemon socket nor direct SSH
works; with `network_access=true` (what agent-fanout already sets) both do,
and the daemon needs no writable directory. Seatbelt's network denial covers
unix sockets, and Codex offers no localhost-only network mode. Untested and
required before adoption: shim latency, PATH order inside Claude Code and
Agentboard shells, Pueue jobs re-entering the shim, corepack interplay,
daemon-down passthrough, and upgrades.

## Fallback

Falling back to local is allowed only while non-execution is provable: worker
unreachable before submit, or queue expiry followed by an acknowledged
cancellation. After any shard starts it is ineligible. Fallback changes a
frozen snapshot into the live worktree and Linux into macOS, so it bypasses
the shim, reports the execution mode, and is bounded so an outage cannot
start many heavy suites at once. `--update` runs do not fall back.

## Open questions for the owner

- Worker upkeep: pinned image with canary, or automatic updates with a canary
  alarm.
- Whether bad flags may be rejected by the repository's runner after a
  container boot (seconds) rather than instantly by Pandora.
- Subdirectory invocations: drop re-rooting and run locally with a notice.
- Worker size, deferred: the sizing model in the triage note overstates
  memory per run by about 2.5× given the measurements above.
