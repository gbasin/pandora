# FIFO admission and queue deadlines

Evidence recorded 2026-09-20 against implementation `44a6f4f` on the existing
OVH worker. This is a twelve-request scheduling probe, not twelve coding agents
and not evidence of Mac responsiveness at the required operating limit.

## Change

Verified remote requests receive monotonically increasing SQLite tickets. Only
the first eligible ticket may obtain the existing resource lease. Remote input
verification determines eligibility, so local invocation or upload order does not
promise execution order. The queue reports position and elapsed waiting.

Queue limits default to 900 seconds. The session launcher accepts an override;
a Docker profile overrides the session value for Docker commands only. Accepted
metadata fixes the effective limit across retry. Worker and follower deadlines
scale with that accepted value.

A dead waiter can be skipped. A dead execution remains a barrier until positive
cleanup evidence exists. The cleanup hook can unblock successors without creating
a terminal test result. The dead request itself remains unresolved. Older workers
must be drained before deployment because they do not honor FIFO tickets.

## Evidence

The local combined suite passed 55 tests: 31 warm-worker tests, 17 routing tests,
and seven output-publication tests. Admission tests use real processes and locks
for ordering, cancellation, dead waiters, dead execution, deadline, duplicate
identity, corrupt queue state, and cleanup receipts.

The [probe](../experiments/fifo/probe.py) submitted twelve requests against an
existing compiled application image. The first held execution while the remaining
requests queued. It then injected client loss, waiting cancellation, a two-second
queue timeout, and worker death in both waiting and running states.

The [results](../experiments/fifo/evidence/2026-09-20/results.json) show:

- Eight surviving commands returned zero with verified cleanup. Execution followed
  tickets 2, 3, 4, 5, 6, 7, 8, and 12 in strict order. Their waits ranged from
  7.0 to 28.0 seconds.
- Waiting cancellation returned 130. The configured two-second wait returned 75.
  Neither started test execution.
- The disconnected client recovered its original attempt. No replacement was
  submitted. Changing its recovery environment to a one-second limit did not
  replace the accepted 120-second policy.
- Both killed workers produced cleanup receipts and no terminal result. Remaining
  work advanced after cleanup. No success was invented for either killed worker.
- A Docker profile limit of 120 seconds overrode the supplied 300-second CLI
  default; the timeout case used its own two-second profile value.
- Postflight found no running Pandora units or containers.

The [queue snapshot](../experiments/fifo/evidence/2026-09-20/queue-before-faults.json)
records ticket order before fault injection. Local raw evidence remains at
`~/.local/state/pandora/fifo-eval-20260920`.

A subsequent [S0-01 regression](../experiments/fifo/evidence/2026-09-20/journey.json)
used the ordinary routed command and default 900-second queue limit. It received
ticket 13, reused its dependency image, passed in 49.1 seconds of execution,
returned the journey report, and verified cleanup.

## Limits

This test uses scripted requests and an existing image, bypassing local
per-worktree routing locks to exercise remote admission. It does not establish
concurrent compiled repair loops, twelve coding-agent sessions, or Mac
responsiveness. Surface/dependency worker death can still require operator cleanup.
Missing terminal reconciliation, resource-failure coverage, and the actual
agent-session trial remain tracked in [Issue #27](https://github.com/gbasin/pandora/issues/27).
