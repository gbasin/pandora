# CPU pin: evidence and the shape of the change

2026-09-26. Worktree `pandora-wt/cpu-pin`, branch `cpu-pin`.

## Why

A run's `PANDORA_CPUS` was a share: host cores divided by the runs admitted
at that instant, computed at the last moment before the command started. The
instance itself saw every host core. Two consequences, both measured on the
live worker (32 cores):

* `check` ran `turbo run typecheck --concurrency=$PANDORA_CPUS` and its peak
  swung between ~3.3 GiB warm and ~11 GiB cold at hint 32: memory appetite was
  a function of who else was admitted. It OOM-killed at its 8 GiB ceiling six
  times on 2026-09-25 16:34-16:58 and twice more 2026-09-26 09:18-09:19.
* Tools that size off `os.cpus()` rather than the env var (Metro, Vite) saw 32
  cores regardless of lanes. `arc` peaks held steady at 7.3-8.4 GiB, grazing
  the `large` ceiling until it OOM'd twice on 2026-09-26 13:47-13:48.

A bimodal peak also breaks size-class learning: clean warm runs teach the
class down, the next cold run OOMs, the OOM resets to declared, repeat.

## Layer 0: the mechanism, measured on the worker

Two clones of `golden-0eafe07892a34a9d`, one with `limits.cpu=8`, one unpinned,
each capped at `limits.memory=16384MiB` and deleted after.

| probe | pinned | unpinned |
|---|---|---|
| `nproc` | 8 | 32 |
| `sched_getaffinity` / `os.cpu_count()` | 8 | 32 |
| Node `availableParallelism()` | 8 | 32 |
| farm peak: `availableParallelism()` workers x 300 MiB | 2.65 GiB | 6.78 GiB |

`limits.cpu=N` pins the cpuset, which is what affinity-based queries read. A
`cpu.max` quota would cap time without changing the count tools see, so it is
not the mechanism. The percentage form of `limits.cpu.allowance` stays the
`cpu.weight` share for fairness under contention.

## Layer 1: the change

* `Scheduler` takes `cpus_per_run`; `cpus_hint` returns it unchanged at any
  lane count, clamped to the host's cores. Admission writes it to the ledger
  row as before.
* `runner.cpus_per_run_of`: `PANDORA_CPUS_PER_RUN` env > `cpus_per_run` in the
  engine root > `max(2, threads // 4)`. `cpus_now` returns it at the last
  moment, so a manifest change lands on the next run.
* `IncusDriver.apply` adds `limits.cpu=<pin>` when the pin is below the host's
  count. `PANDORA_CPUS`, `limits.cpu` and `nproc` are one number.
* `[worker] cpus_per_run = 0` in versions.toml (0 derives), `provision.sh`
  writes `engine_root/cpus_per_run` beside `max_running`, `pandora worker
  status` reports `cpu pin`.
* The running line prints `cpus 8` instead of `cpus hint 8`; docs agree.
* The local lane is untouched: it is a soft hint by design, and the machine a
  local run sees is the real one.

## What this does not fix

A single process with a big appetite (one bundler at 8 GiB) OOMs on two cores
too. The pin removes the correlation between neighbor count and peak; the
memory ceiling remains the backstop for genuinely oversized jobs.
