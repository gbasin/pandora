# Surface shard shape on the 4-core worker, 2026-09-23

The question: is `ubuntu@WORKER` (4 vCPU, 15.6 GiB) too small for the
surface job's configured shape (2 shards, `SURFACE_WORKERS=1`), and which shape
is fastest. Answer: the box is not too small for the configured shape, but that
shape leaves about a third of the CPU idle. Four browsers in total is the
knee. **2 shards x 2 Playwright workers** was the fastest shape measured
(346 s for 433 tests) and uses less memory than 4 x 1.

All runs were `pnpm test:surface web` through the shim in the acme
PR worktree `acme-wt/pandora-v02` (branch `agent/pandora-v02`, PR #1500).
Each ran alone on the worker except the baseline. CPU figures come from
`vmstat 5` sampled on the worker during each run.

## Results

with `verified: true` (observed ids exactly the planned partition). No shard
queued behind admission and none was refused.

## Reading it

**CPU is the limit.** Memory is not. One browser keeps about 1.6 of the 4
cores busy (41%). With 2 browsers (2 x 1 or 1 x 2), the box is 60-68% busy.
With 4 browsers (4 x 1 or 2 x 2), it saturates: 4 x 1 averaged 91% busy with a
run queue of 11. The page cache fell to about 200 MiB free, but nothing
swapped. Doubling from 2 to 4 browsers saved 20-25% of wall time, not 50%.
More than 4 browsers on this box would be useless.

**How the browsers are split matters less than how many there are.** With the
same browser count, Playwright's own worker pool gets the same result as
Pandora's fan-out, or a slightly better one: 1 x 2 took 452 s against 466 s for
2 x 1, and 2 x 2 took 346 s against 364 s for 4 x 1. The pool costs less:

* one instance instead of two, so one clone, one graft and one set of
  node/Vite processes;
* shards with a single browser have skew. The slowest of 4 shards ran 25 s
  longer than the fastest, and fan-out always waits for the slowest shard.

**Memory per shard grows with workers, but total memory falls.** One browser
per shard peaks at about 2.6 GiB, two per shard at about 3.3 GiB (1 x 2 peaked
at 3.6 GiB). 2 x 2 uses about 6.5 GiB for the whole run against about 9.8 GiB
for 4 x 1. That matters for admission: `surface` is `size = "medium"`, whose
ceiling is 4096 MiB, and the learned reservation is p95 x 1.25 capped at the
ceiling. With workers at 2, each shard reserves the full 4096 MiB (3.3-3.7 GiB
x 1.25 is above the cap), so 2 x 2 reserves 8 GiB. With workers at 1, a shard
reserves about 2.7 x 1.25 = 3.3 GiB, so 4 x 1 reserves about 13 GiB. That
leaves no room beside it for a journey (`large`, 8192 MiB) on this box.

The peak history is kept per (repo, job), not per shape. Today's 2-worker
peaks (3.2-3.7 GiB) are now in the `surface` history. The next 4 x 1 run will
therefore probably reserve the 4096 MiB ceiling per shard, 16 GiB in total, and
its fourth shard may queue. This was not checked. The shape belongs in the job
configuration so that the history describes one shape.

**A neighbouring journey costs little.** The baseline 2 x 1 run beside a
journey took 486 s. The same shape alone took 466 s, so the journey cost 4%.

## Recommendation

Set the surface job's default to **2 shards with `SURFACE_WORKERS = "2"`**:

* It was the fastest shape measured, 346 s against 466 s for today's default
  (-26%).
* It reserves 8 GiB. A second surface run or a journey can still be admitted
  beside it, and would share the CPU.
* It uses two instances, not four, so less clone, graft and teardown work and
  less skew.

Keep `max = 8`. On a larger worker, the right count is total browsers equal to
cores, so `SURFACE_WORKERS` should really follow `PANDORA_CPUS`. That is gap 6
in the sharding note and still needs environment templating. On this box,
leave `PANDORA_SHARDS=4` as an explicit override, not a default: it is 5%
slower than 2 x 2 and reserves 60% more memory.

## Caveats and what was not measured

* **One run per shape.** Variance was not measured. The gap between 2 x 2 and
  4 x 1 (18 s) and between 1 x 2 and 2 x 1 (14 s) is in the range run-to-run
  noise could plausibly cover. The ranking of 4 browsers over 2 over 1 is not.
* **Not measured:** 1 x 4 (one instance with four Playwright workers), which
  could beat 2 x 2 for the same reasons 1 x 2 beat 2 x 1. 2 x 3 and 4 x 2 were
  not measured either (oversubscribed on 4 cores). `SURFACE_CI=1` (retries,
  Playwright's own CI worker count of 4) was not tested.
* **Not run:** the journeys catalog (`pnpm journeys`). The owner stopped the
  work before Part 2. There is no catalog wall time, peak or pass count on the
  worker yet.
* The desk run finished before the stop arrived. It is reported above as one
  data point, not as a benchmark.
* `SURFACE_WORKERS` is honoured: the runner passes it as `--workers=N`.
  `SURFACE_CI = "0"` clears `CI`, so Playwright used no retries, and the
  `workers` value in `playwright.config.ts` (`CI ? 4 : 1`) did not apply.
* During the day, swap pressure paused this Mac's local lane. That does not
  affect these remote timings.
* In the 1 x 2 and desk runs, `pandora` reported `free lanes 3`, not 4, with
  nothing else remote running. It did not constrain those runs, which asked for
  at most 2. It was not investigated.
* `pandora doctor` warned that the real pnpm is a corepack shim. That does not
  affect remote runs.
* Two Claude sessions crashed mid-run (during 2 x 1 and 4 x 1). The runs
  continued on the worker and their results come from `pandora result`, so the
  numbers are unaffected. The CPU samples for 4 x 1 cover about 340 s of its
  364 s.

The acme worktree's `pandora.toml` was edited to `SURFACE_WORKERS = "2"`
for the 2 x 2, 1 x 2 and desk runs, then restored with `git checkout`. No acme
change was committed or pushed.
