# The fallback policy: one path, through the local lane, 2026-09-22

On 2026-09-22 a `pnpm test:surface desk` typed in an Eichler worktree ran 302
browser tests on this Mac for 3.3 minutes. Nothing was broken. Every component
did what it was written to do. The worker's ledger -- which did not yet know
about sharding -- refused the submission, the daemon turned that refusal into an
error frame, and the shim did what it had always done with an error frame that
arrived before `accepted`: it printed one line and `exec`ed the real pnpm.

The rule that produced it is correct and is not changing: **before `accepted`
the command provably has not run, so falling back is permitted.** What was
missing is the second question. Permitted is not the same as wise, and nobody
was asking whether a 302-test browser suite belongs on a laptop.

This note records what now asks it.

## The exact sequence that caused the accidental run

| # | Where | What happened |
|---|---|---|
| 1 | `bin/pnpm` | claimed prefix `test:surface` in the marker, handed off to `pandora.client.shim` |
| 2 | `daemon.serve_run` | classified, pre-flight validator passed, worktree frozen and shipped |
| 3 | `worker.submit` | the engine answered `{"ok": false, "code": "rejected"}` -- a pre-sharding ledger refusing a sharded submission |
| 4 | `daemon.serve_run` | `except EngineError` → `self.deny(conn, 'rejected', …)` |
| 5 | `shim.main` | `frame['t'] == 'error'`, code not in `('invalid-arguments', 'busy')` → `give_up(…)` |
| 6 | `shim.run_local` | took one of two fallback slots, `subprocess.call(['pnpm', 'test:surface', 'desk'])` |
| 7 | this Mac | 302 tests, **3.3 minutes**, one browser, no queue, no admission, no receipt |

Steps 4-6 are three components agreeing that an unexecuted command may be run
here, and none of them knowing that the job is `large`.

**The test that now prevents it** is
`pandora/tests/test_fallback.py::OneFallbackPath::test_a_large_job_is_refused_rather_than_run_here`.
It stands up a real daemon over a real socket, has the fake worker raise
`EngineError({"code": "rejected"})` on submit -- step 3, exactly -- and asserts
three things: exit **70**, an error naming `size large`, and that the job's
marker file **does not exist**. The last assertion is the one that matters: it
fails if anything anywhere ran the command.

Six more tests in the same class assert that each *other* cause
(`worker-unreachable`, `snapshot-failed`, `transfer-failed`, `queue-timeout`,
`admission-refused`, `engine-error`) reaches the same decision for a `small`
job, and lands it in the local lane with `reason: fallback:<cause>` rather than
in a bare `exec`.

## The behaviour table

`decide()` in `pandora/client/fallback.py` is the only place any of this is
answered. Its inputs are the cause, the job's size class, whether the run writes
back, and what the job declared.

| Cause | Where it is raised | `small` / `medium` | `large` / `xlarge` | with `--update` |
|---|---|---|---|---|
| `worker-unreachable` | `worker.submit` | local lane | refuse, 70 | refuse, 70 |
| `snapshot-failed` | `snapshot.freeze` | local lane | refuse, 70 | refuse, 70 |
| `transfer-failed` | `transfer.send` | local lane | refuse, 70 | refuse, 70 |
| `queue-timeout` | engine, before `accepted` | local lane | refuse, 70 | refuse, 70 |
| `admission-refused` | engine, before `accepted` | local lane | refuse, 70 | refuse, 70 |
| `engine-error` | any other engine refusal | local lane | refuse, 70 | refuse, 70 |
| `daemon-unreachable` | the shim, no daemon | slot budget | refuse, 70 | refuse, 70 |
| `daemon-closed` / `handshake-timeout` | the shim, no answer | slot budget | refuse, 70 | refuse, 70 |
| **after `accepted`** | `daemon.execute` | **infra failure, 70** | **infra failure, 70** | **infra failure, 70** |

A job's own `fallback = "local"` or `"refuse"` overrides the size column in both
directions. A `[fallback]` table with an `on` list overrides it only for the
causes it names; every other cause is refused.

Three verdicts and what each means in one line:

* **local lane** -- `serve_local` with the job's size class: the same queue, the
  same memory admission, the same exclusivity rules, the same receipt, a row in
  `pandora ps`. Twelve agents whose worker just died queue behind one budget.
  Announced on stderr as `pandora: <cause> (<detail>); <reason>`, and recorded
  in the receipt as `lane: local, reason: fallback:<cause>`.
* **refuse** -- exit **70**, one line naming the cause and `PANDORA_OFF=1`.
  Nothing runs anywhere.
* **slot budget** -- only when the daemon itself is gone. There is no local lane
  to admit into, so the bound is the `fallback_slots` file locks, and the notice
  says that is what happened.

### What changed in who decides

The shim no longer decides anything while the daemon is alive. **Every** error
frame from the daemon is final and carries its own exit code; the client's only
remaining verdict is `passthrough`, which means Pandora has no opinion about
this invocation at all (not enrolled, not claimed, or a subdirectory invocation
naming a path) and the command runs as if the shim were not installed.

When the daemon *is* gone, the client applies the same policy from the enrolment
marker, which `pandora enrol` now writes a `policy <size> <action> <writeback>
<prefix…>` line into for every claimed form. A marker written before this rule
exists has no such lines; an unknown job is decided as `large` and refused,
because a client that cannot say how big a job is has not earned the right to
start it here. The POSIX shim ignores the new lines -- its `case` matches four
keys -- so the 4.8 ms non-enrolled path is unchanged.

## Configuration keys and defaults

### `pandora.toml`, per job

| Key | Values | Default | Notes |
|---|---|---|---|
| `fallback` | `"local"` \| `"refuse"` | *undeclared* | Undeclared is a third answer, not a default: the size class decides. The v0.1 table form (`action`/`on`/`notice`) still loads, and `action = "fail"` normalises to `refuse`. |
| `cancel` | `{ signal = "SIGINT"\|"SIGTERM"\|"SIGHUP"\|"SIGQUIT", grace_ms = N }` | `{ SIGTERM, 15000 }` | `SIGKILL` is not offered: it is what the grace escalates to, never what a job may ask for. `grace_ms` 0-3,600,000. |
| `drift` | `"off"` \| `"warn"` \| `"fail"` | *inherit `[local] drift`* | **Recommendation: `small` jobs use `off`.** Freezing eichler is ~4,900 files; it is right for a 60-second suite and absurd for a 4-second `node --test`. |
| `outputs` with `kind = "evidence"` | paths or globs inside the worktree | none | `where = "local"` only. A remote job's paths are `artifacts`; a local job brings nothing home, so what it declares is what a reader of the receipt must look at. |

A local job may now declare `outputs`, but only of kind `evidence`; a remote job
may not declare `evidence`. Both are refusals with the allowed kinds printed.

### `~/.config/pandora/config.toml`, `[local.pause]`

| Key | Default | What it means |
|---|---|---|
| `enabled` | `true` | |
| `sample_seconds` | `3` | A reading is reused for this long. Sampled when something wants in, never on a timer. |
| `swap_growth_mib_per_minute` | `256` | Growth between consecutive samples. Level is not a signal: 4 GiB of swap sitting still is a Mac that swapped yesterday. |
| `psi_full_avg10` | `20.0` | Linux `/proc/pressure/memory`, `full avg10`. |
| `free_percent` | `5.0` | macOS `memory_pressure -Q`, falling back to the `vm_stat` sum of free + inactive + speculative + purgeable. Raw `Pages free` is **not** a signal: on a healthy 16 GiB Mac it sits near 0.4 %. |
| `load_per_cpu` | `8.0` | The backstop. `0` disables it. |
| `max_wait_seconds` | `300` | Per job. Then exit **70** -- never a run anyway. |

Unknown keys in `[local.pause]` are refused rather than ignored: a misspelled
threshold that is silently dropped is a gate that is silently off.

## The pause gate, and what it replaces

`notes/pueue-replacement-2026-09-22.md` open question 4 -- "should a local
failure ever pause anything?" -- is answered: not a *failure*, a *machine*.
`assertHealthy` paused a Pueue group after an unclean job, which was a proxy for
"this box is in a bad way". The local executor holds its own process group, so
the specific failure `assertHealthy` guarded cannot happen; what it also did,
and nothing replaced, was stop an agent piling onto a broken machine.

So the gate is about the host and nothing else. Both probes are ~3 ms and both
are honest about their platform. A job held at the gate has provably not run,
which is what makes the whole thing safe: it is a pre-accept wait, announced as
`pandora: local lane paused: <evidence>`, and the alternative to waiting is not
running, so a job that waits the whole of `max_wait_seconds` exits 70.

Measured by hand on this Mac with `free_percent = 99` to force the gate shut:

    $ pandora ps
    local lane PAUSED: 48.0% of memory free, limit 99.0% (max wait 2s)
    run            lane   state      remote            exit  command
    330292fa5e67   local  refused    -                   70  pnpm check

    $ pnpm check
    pandora: local lane paused: 48.0% of memory free, limit 99.0%
    pandora: this Mac has been under pressure for 2s (48.0% of memory free,
    limit 99.0%), so nothing new is being started here. Wait, or run it with
    PANDORA_OFF=1.        # exit 70

    $ pandora stats | tail -1
      pause gate: PAUSED (48.0% of memory free, limit 99.0%), 1 episode(s),
      2.4s paused, 1 job(s) delayed, 1 refused

The counters live in `<state>/pause.json` and survive a daemon restart.

## Cancel: what is honoured where

Open question 1 of the Pueue note is answered for the local lane and half
answered for the remote one.

**Local.** `Supervisor` sends the job's signal to the whole process group, waits
`grace_ms`, then SIGKILLs the group. `trap 'INT'` in a test child is caught and
its handler runs; a child that traps and ignores both is killed when the grace
expires. Two tests, both against real processes.

**Remote.** A remote cancel is an **instance destroy**: the run dies whatever
happens and the receipt proves the machine is gone. The contract still travels
-- `classify.build_plan` puts `cancel` in the plan, `worker.submit` ships the
plan whole into the attempt's `request.json`, and `runner.supervise` reads it
from there into `Limits` -- and `IncusDriver.kill` now sends that signal to the
guest process group, waits the grace, and then `kill -9`. **This cost 24 lines
and no ledger column**, which is why it was implemented rather than deferred: an
attempt written before this existed has no `cancel` in its request and reads as
`SIGKILL` with a zero grace, which is the old behaviour exactly.

Only a *cancel* gets a grace. An `oom` or a wall timeout is a machine that is
already not working, and waiting politely on it is how a thrashing instance
holds the box for another four minutes.

**Unverified:** the remote half has unit tests at both seams and has never run
on the worker. No real instance has been cancelled with a non-default signal.

## Cleanup markers: declared, not discovered

Open question 2 -- should the local lane set `EICHLER_VALIDATION_DIRECTORY`? --
is answered **no**. Pandora does not invent a directory and hope the job writes
its marker into it. A job declares where it writes:

    outputs = [{ kind = "evidence", paths = ["tmp/validation/*/cleanup-required",
                                             "tmp/validation/*/result.json"] }]

and the receipt records each path with `present` and `bytes`. A declared path
that is absent is a row saying so, not a silence. Globs expand against the
worktree; a literal path is recorded as missing when it is not there.

This is tests-only on the Pandora side and needs no eichler edit to *work*: the
two out-of-tree consumers (`tools/browser-integration/run.mjs`,
`apps/agent/tools/test-ios.mjs`) keep writing wherever eichler tells them to.
What the eichler PR gains is a `pandora.toml` that names those paths, so the
receipt is the place to look rather than a directory somebody has to know about.

## Subdirectory invocations

The slice chose "run locally with a notice" over re-rooting, because re-rooting
silently changes which files a selector names. That is true of *some* argv and
not others, so the rule is now about the argv rather than about the directory:

* no token names a path -- no `/`, and no token that exists relative to where it
  was typed -- the job is **re-rooted** to the worktree root and announced:
  `pandora: running from the worktree root; you typed this in apps/agent and no
  argument names a path`;
* otherwise the command **passes through** locally with `pandora: run from the
  repo root to route`.

`pnpm journey S0-01` means the same thing everywhere, because the repository
resolves `S0-01` against its own catalogue. `pnpm unit src/x.test.ts` does not.
The filesystem check is what catches the third case, `pnpm unit x.test.ts` with
no slash and a real file beside it.

`matching.subdirectory = "reject"` is unchanged and still refuses outright.

## Where the tension is, and it is not resolved

A subdirectory pass-through runs a *claimed heavy command* locally, unbounded
and unqueued, which is the shape of the accident this note is about. It is
allowed because it is not a fallback: Pandora never claimed that invocation, so
the alternative is refusing a command a person typed in a directory Pandora
happens to dislike. It is recorded in the passthrough log with its reason, and
`pandora stats` counts it. If it turns out to be a hole, the fix is the same
policy applied to passthroughs, and the data to decide that with is now being
collected.
