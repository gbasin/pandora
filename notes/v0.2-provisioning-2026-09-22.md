# Worker provisioning, 2026-09-22

`ubuntu@WORKER` is now a machine somebody else could make again. One
command builds it, one command proves it, one command says what it is, and one
command keeps it from filling up. Everything below was measured on that box
between 11:45 and 12:20 UTC, including a real reboot.

Branch `v0.2/assembly`. `pandora/worker/` is new (1,410 lines); the executor
gained a disk quota, a pool reader and an inventory; the engine gained a
28-line disk hook and a 4-line pins field. 305 tests, of which 33 are new.

## What exists

| Command | What it does |
|---|---|
| `pandora worker provision [--host] [--device\|--loop-file] [--versions]` | ships one POSIX `sh` script over SSH, runs it, reports every step, then runs the canary and writes the ready state from its verdict |
| `pandora worker status` | manifest, installed versions, drift, pool usage, admission gate, goldens, last canary, ready state |
| `pandora worker canary [--journey F] [--surfaces F] [--mark]` | 26 checks, ~100 s |
| `pandora worker gc [--dry-run] [--keep N]` | leaked run instances, leaked volumes, goldens past the keep count, with a receipt |
| `pandora worker goldens` | fingerprints, repo, referenced and exclusive bytes, pinned or not, last use |
| `pandora worker pins --toolchain F [--source D]` | resolves a toolchain to its base image fingerprint, lockfile digest and registry manifest digests |
| `pandora worker reconcile\|retain\|stats` | the engine's own three, moved off the client daemon so they work on a worker no client has adopted |

The split is by *where the code executes*. `versions`, `provision`, `remote`
and `cli` run on the Mac. `service`, `canary`, `gc`, `goldens`, `facts` and
`pins` run on the worker, shipped inside the same content-addressed engine
bundle the engine uses -- they read cgroups, btrfs qgroups and the Incus socket
several times a second, which is the reason the driver lives there too.
`bundle.MEMBERS` gained seven files; `bundle.call`'s shape gained a sibling,
`Remote.call`, that names the module.

## Five things the box taught

**The pool is adopted, never re-created.** The first `provision` obediently
made an 18 GiB `~/pandora/pool.img` beside the live pool's
`~/incus-exec/pool.img` and pointed the boot unit at the new, empty one. That
would have survived exactly one reboot and lost every golden. `provision` now
reads the loop device behind the pool's mount point (`findmnt`, `readlink -f`,
`losetup -O BACK-FILE`) and adopts that file. A pool that already exists is
never touched.

**`limits.disk` on btrfs limits `referenced`, not the run's own writes.** Incus
writes `btrfs qgroup limit <size>` on the instance's subvolume, and a clone
references every extent it shares with its golden from the instant it exists.
So a 1 GiB quota on a clone of a 4.25 GiB golden is instantly over quota, and
btrfs then refuses *every* later qgroup operation on that group -- which is how
the first attempt produced `unable to limit requested quota group: Disk quota
exceeded` and an instance that could not start at all. `IncusDriver.quota` now
reads the clone's referenced bytes first and refuses with the arithmetic rather
than producing an unstartable machine. `run_disk_gib = 12` therefore gives a run
about 8 GiB of its own writes over a 4 GiB golden. **This is the number an
operator has to understand**, and it is in the docstring, the manifest comment
and `docs/worker-rebuild.md`.

**The loop device number does not matter.** `incus storage show pandorapool`
records `source: 0de97da8-...` -- a filesystem UUID -- with `/dev/loop0` only
in `volatile.initial_source`. So the boot unit can attach the file to any free
loop device. That is why `pool-attach` is four lines and not a fight with
`max_loop`.

**iptables rules do not survive a reboot and nothing in the POC noticed**,
because the POC never rebooted. The bridge's two `FORWARD ... ACCEPT` rules are
now a unit of their own (`pandora-net.service`), ordered after
`incus-startup.service`, whose script waits up to 60 s for the bridge to exist
before inserting them.

**An instance is "ready" before `docker.service` is loaded.** `wait_ready`
returns as soon as `/run/systemd/system` exists, which is early enough that
`systemctl start docker && docker info` short-circuits into an empty answer.
The canary's first run reported `nested dockerd up: false` on a golden whose
dockerd works fine. It retries now.

## The reboot, and the one surprise

The box went down on **kernel 7.0.0-14-generic** and came back on
**7.0.0-31-generic**. Nothing in the versions manifest changed, because the
manifest pins dpkg packages and the running kernel is not one of them: an
upgraded `linux-image` had been sitting installed and unbooted, almost
certainly put there by the `unattended-upgrades` this work has now disabled.

Everything still passed -- the canary ran clean on the new kernel twice -- but
"the machine the canary passed on" and "the machine now taking work" were
briefly different machines and nothing said so. `status` now records the kernel
beside the ready state and reports a changed one as drift, which makes the
worker read `drifted` rather than `ready` until somebody re-runs the canary.

Nothing else changed across the reboot: same pool, same two goldens, same
project and profile, same forwarding rules, no leaked instances, no leaked
volumes, no veths.

## Golden input pinning: built, resolved, not yet applied

`Toolchain.pins` carries the resolved inputs and is folded into the
fingerprint. An *empty* `pins` hashes exactly as the field did not exist, so
the two goldens on the box are not orphaned by the change -- deliberate, and
tested.

Resolution runs on the worker (`pandora worker pins`) because that is the
machine with the image server, the registry route and the shipped source:


`2775adec0be404dd` unpinned becomes `aa7811787062efc9` pinned. The registry
lookup is stdlib `urllib` with an anonymous pull-scope bearer token -- there is
no Docker on the host by design, so `docker manifest inspect` was not an
option, and installing one would have been a second image store on the same
disk. `prepare` launches `images:<fingerprint>` and pulls `image@sha256:...`
when pins are present.

**Nothing on the box is pinned yet.** Pinning the two goldens means building
two new ones, which is ~9 GiB in a pool with 8.60 GiB free. That is the next
change and it wants the pool on a real device first.

## What is still manual

1. **Pinning the live goldens.** See above. The code is there and proven to
   resolve; the goldens are not rebuilt.
2. **The pool is still a loop file on this box**, adopted from the POC. The
   systemd unit makes it survive a reboot, which was POC blocker 4, but a real
   deploy passes `--device /dev/sdb` and none of the loop machinery runs. That
   path is written and **NOT RUN**: there is no spare block device here.
3. **`golden_keep` has never evicted a golden on this box.** The keep policy is
   unit-tested against a real ledger and a fake host, and the live sweep has
   only ever had two goldens and a keep of 2. The eviction path is proven in
   tests, not on the machine.
4. **The leaked-volume sweep has never fired.** Every destroy receipt on this
   box has been clean, so there has never been a volume without an instance.
   Tested, not observed.
5. **Cut-over is a written procedure, not a command.** `docs/worker-rebuild.md`
   says to close the old worker's floor by writing to `disk_floor`, wait for
   `stats` to empty, and edit one line of client configuration. There is no
   `pandora worker drain` and no `pandora worker retire`.
6. **Drift is reported, never corrected.** `status` says a package is at the
   wrong version; fixing it means re-running `provision`, and re-running
   `provision` does not *downgrade* anything.
7. **The canary's toolchains are files a person passes.** `--journey` and
   `--surfaces` take paths, shipped if they exist locally. They are not read
   from the repository's own `pandora.toml`, so a repository that changes its
   toolchain does not automatically change what the canary proves.
8. **`pandora-engine.service` only reconciles.** It is a lingering user unit
   that waits for Incus, makes the layout and runs one `reconcile` at boot. It
   is not a daemon and there is nothing long-running on the worker.
9. **No GC timer.** `gc` is a command a person runs. The rebuild doc says
   weekly; nothing enforces it.
10. **One architecture, one distro, one repository.** x86_64 Ubuntu 26.04 and
    eichler, as before.
