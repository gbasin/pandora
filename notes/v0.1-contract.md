# Pandora v0.1 command contract and acceptance

Current v0.1 scope, updated 2026-09-20. This document defines the command
contract and the evidence required before everyday use. The root README describes
current behavior. Dated notes preserve experiment results. The v0.1 GitHub issue
tracks execution progress.

## Agreed scope

Agents and worktrees remain on the dedicated Mac. Pandora routes selected
validation workflows and selected Docker command patterns to a Linux worker.
Profiles live outside the target repository. Other engineers need no changes.
Existing subscriptions and agent launchers remain in use.

The required coding loop is build, run or test, inspect evidence, edit locally,
and rerun. Separate shell calls must work. One service-backed validation workflow
is required before everyday use. Evaluate both Codex and Claude Opus.

Commands use frozen input snapshots. A local edit after submission never changes
accepted input or becomes reported as tested. A changed local source makes an
older result stale. An active request is reported and never automatically
replaced. After client loss, accepted work finishes within its deadline and retry
reconnects to the same run.

Image tags are private to each worktree and survive launcher restarts. Rebuilding
a tag publishes its new image only after success. A run resolves its image when
admitted, so a later rebuild or tag removal cannot change that accepted run.

Declared workspace outputs are exclusively managed generated directories. A
destination must be an ignored directory with no tracked files. Symlink,
traversal, and mixed source/output destinations are rejected. After a successful
command and verified retrieval, Pandora replaces each declared directory with a
new generation and retains its prior generation in the attempt publication
directory. Retrying an interrupted delivery resumes the same result without a new
execution. Multiple declared directories may publish separately; v0.1 does not
promise one transaction across them. General source writeback and arbitrary
mixed-directory merging are deferred.

Docker runs execute in the foreground. Validation owns the startup, readiness,
and cleanup of its supporting services. Detached services and forwarded preview
ports across commands are outside v0.1.

Unsupported Docker commands stop with actionable feedback inside routed sessions.
They do not fall back locally. The wrapper is not OS enforcement: absolute paths
and environment changes can bypass it. No security or universal-interception
claim follows.

Admission must preserve first-in, first-out order for eligible requests. Queue
waiting is bounded by a profile-configurable timeout whose default is 15 minutes.
Timeout feedback identifies the request and does not start local validation.

## Accepted command surface

The routed validation commands are:

```sh
pnpm [run] test:surface borrower-web [file selectors]
pnpm [run] validate surface borrower-web [file selectors]
pnpm [run] journey S0-01
pnpm [run] validate journey S0-01
```

`S0-01` is the single v0.1 service-backed workflow. Its profile owns private
service startup, readiness, teardown, and the returned journey report. Other
journey IDs, journey flags, and the full journey suite remain outside this
command surface.

The routed Docker commands are:

```sh
docker build [-f RELATIVE_DOCKERFILE] -t TAG .
docker run --rm [-v "$PWD:CONTAINER_PATH[:ro]"] TAG [COMMAND [ARG...]]
docker image rm TAG
```

Docker forms run from the worktree root. A profile opts in and declares its
Dockerfile, permitted mount destinations, generated-output paths, runtime
configuration, resource limits, and deadlines. Parse argv rather than shell text.
Reject unsupported flags and conflicting options before submission, with the
rejected argument and a supported example when one exists. Preserve argument
boundaries, command overrides, stdout, stderr, command failure, and calling-shell
pipeline semantics.

The Docker grammar excludes detached or interactive runs, published ports,
privileged mode, host networking, host devices, Docker socket mounts, arbitrary
host mounts, external build contexts, registry pushes, and general Compose CLI
routing. Images must be built through Pandora. Arbitrary registry-image execution
is an extension.

## Source, outputs, and failure evidence

Capture dirty tracked files and nonignored untracked files. Exclude credentials,
local dependencies, machine caches, and ordinary ignored files. A profile may
declare a necessary ignored input explicitly. These exclusions are not a secret
scanner. Apply the selected Dockerfile's ignore rules inside a supported build
snapshot. If an exclusion removes required input, report that limitation before
execution.

Record and verify a manifest of submitted bytes. Record the command, selectors,
source digest, runtime image, limits, and run ID. Each job gets its own writable
workspace, processes, and network environment. Shared caches require understood
concurrency and trust behavior. Execution containers never modify frozen
snapshots.

Retrieve available failure diagnostics after nonzero exit, timeout, or OOM. Keep
failed or partial outputs in the run artifact directory. Report delivery status
separately from the remote command result. Never report partial delivery as a
completed command. Print absolute local artifact paths and identify remote source
paths. Profiles define visible artifact retention and size limits.

## Tools, caches, and resource limits

Pandora uses SSH and rsync for transport, Docker for execution, and systemd for
independent supervision. Dependency preparation uses BuildKit with persistent pnpm
cache mounts. BuildKit and supporting services count toward worker CPU and RAM
limits. Bound preparation, service startup, execution, artifact collection, and
cleanup. Test containers do not receive unrestricted host Docker-socket access.

Keep dependency images separate from build outputs. A matching installation recipe
reuses its image. Changed installation inputs prepare a matching image under
admission limits and an independent deadline. Concurrent preparation for the same
key must deduplicate. The key includes toolchain, platform, recipe, lockfile,
package manifests, patches, and other installation inputs. Unsupported install
hooks fail clearly rather than reuse stale state.

Use the build tool's native cache for compilation. Each run keeps its own mutable
build directory and installed dependencies. Test invalidation across source,
dependencies, environment, toolchain, and platform changes. Capacity expansion
requires measured limits and does not automatically buy more worker capacity.

## Required acceptance evidence

Every scenario records command, snapshot or image identity, queue, preparation,
run, and transfer times, terminal result, cleanup, and returned evidence. Preserve
evaluator prompts and agent actions.

| Contract area | Required evidence |
| --- | --- |
| Familiar command | Codex and Opus use normal shell startup and separate calls; unrelated commands retain behavior |
| Frozen source | Dirty edits, new files, renames, deletions, and explicitly declared ignored inputs produce the intended snapshot; sibling worktrees stay excluded |
| Source mutation | Capture rejects inconsistency; later edits cannot alter accepted input or become a false current-source pass |
| Repair loop | An agent reads failure evidence, repairs local source, reruns, and obtains a result for the new bytes without coaching or fallback |
| Docker image lifecycle | Tags resolve across calls and launcher restart; mounted and unmounted source follow the stated semantics; same tags in two worktrees stay isolated; failed rebuild preserves the prior image |
| Dependency preparation | A missing image prepares automatically within limits; same-key preparation deduplicates; failure is observable and does not become a test failure or local fallback |
| Compiled build | Cold and identical builds plus source, dependency, and toolchain changes demonstrate invalidation and output return |
| S0-01 lifecycle | Services and mutable data are isolated; success, failure, cancellation, and worker loss have verified cleanup or an explicit unresolved record |
| Generated-output publication | Replaced and deleted generated files, retained prior generations, ignored destinations, unsafe paths, and interrupted delivery follow the ownership contract |
| Recovery | Client or SSH loss preserves the accepted run; retry recovers it without duplicate execution; changed source is stale |
| Admission and cancellation | Duplicate invocation reports existing work; eligible requests preserve FIFO order; timeout and cancellation affect only owned resources |
| Resource outcomes | Build OOM, test OOM, timeout, disk exhaustion, artifact limits, and missing terminal records have distinct actionable outcomes and never become false success |
| Unsupported Docker syntax | No submission or local execution occurs; feedback lets an agent select a supported form |

Scripted probes establish semantics before agent trials. Repair-loop trials use both
agent CLIs without prompts that supply a recovery strategy. A wrong-source pass,
lost output, duplicate execution, unannounced local fallback, or unverified
cleanup fails acceptance even when the launcher exits successfully.

## Deferred and optional extensions

The following are outside v0.1: general source writeback, mixed source/output
merging, detached services, cross-command forwarded ports, identity migration,
arbitrary registry images, arbitrary Docker and Compose routing, continuous sync,
multi-host scheduling, interactive previews, native macOS builds, universal
command routing, and replacement of target-repository CI.

Twelve-agent capacity, interactive Mac responsiveness, broader Docker
compatibility, and additional service-backed workflows are rollout evaluations.
They may inform a later operating limit. They are not v0.1 acceptance criteria.
