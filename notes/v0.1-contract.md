# Pandora v0.1 command contract and acceptance

Current v0.1 scope, updated 2026-09-20. This document defines the command
contract and the evidence required before everyday use. The root README describes
current behavior. Dated notes preserve experiment results. [Issue #27](https://github.com/gbasin/pandora/issues/27)
tracks execution progress.

## Agreed scope

Agents and worktrees remain on the dedicated Mac. Pandora routes selected
validation workflows and selected Docker command patterns to a Linux worker.
Profiles live outside the target repository. Other engineers need no changes.
Existing subscriptions and agent launchers remain in use. v0.1 schedules on one
server with configurable shard concurrency. Multi-server placement and recovery
are the next extension, not a v0.1 requirement.

Eichler prioritizes long-running tests: focused and full journeys and browser
surfaces. Fast standalone builds, checks and unit tests stay local. Builds needed
by a remote test run with that test. Supported Docker behavior remains available;
compiled-build throughput is not the primary capacity workload.

The required coding loop is build, run or test, inspect evidence, edit locally,
and rerun. Separate shell calls must work. One service-backed validation workflow
is required before everyday use. Evaluate both Codex and Claude Opus.

Commands use frozen input snapshots. A local edit after submission never changes
accepted input or becomes reported as tested. A changed local source makes an
older result stale. An active request is reported and never automatically
replaced. After client loss, accepted work finishes within its deadline and retry
reconnects to the same run.

Image tags are private to each worktree and survive launcher restarts. Rebuilding
a tag publishes its new image only after success. A run resolves and reserves its
image at submission, before queueing, so a later rebuild or tag removal cannot
change that accepted run.

Build outputs are exclusively managed generated directories. A
destination must be an ignored directory with no tracked files. Symlink,
traversal, and mixed source/output destinations are rejected. After a successful
command and verified retrieval, Pandora replaces each declared directory with a
new generation and retains its prior generation in the attempt publication
directory. Retrying an interrupted delivery resumes the same result without a new
execution. Multiple declared directories may publish separately; v0.1 does not
promise one transaction across them. General source writeback and arbitrary
mixed-directory merging are deferred. Declared tracked journey expectations use
the separate publication contract below.

Docker runs execute in the foreground. Validation owns the startup, readiness,
and cleanup of its supporting services. Detached services and forwarded preview
ports across commands are outside v0.1.

Unsupported Docker commands stop with actionable feedback inside routed sessions.
They do not fall back locally. Local escape requires human control. The wrapper is
not OS enforcement: absolute paths and environment changes can bypass it. No
security or universal-interception claim follows.

Scheduling policy belongs to operator configuration, not agent commands. The
current implementation uses one worker slot with FIFO admission between child attempts. Sharded execution must provide
a fair-turn policy between waiting invocations at shard boundaries, with strict
FIFO available as a configuration choice. Running shards are never interrupted
to admit another invocation. Worker CPU/RAM and per-invocation concurrency limits
include supporting services and internal test workers. Queue waiting is bounded
by a profile-configurable timeout whose default is 15 minutes. Timeout feedback
identifies the request and does not start local validation. One cumulative waiting
budget applies to the invocation across shard dispatches. Dispatching a shard
does not reset it. With parallel shards, count elapsed queue time once while an
invocation has waiting work and no admitted shard. Pause that clock while any of
its shards runs, including preparation and cleanup. Do not sum overlapping
shard waits. Execution time has a separate deadline. The accepted budget
and accumulated waiting time survive client reconnects.

Suite validation stops dispatching new shards after the first test failure by
default. Already-running shards finish within their deadlines. The suite dispatcher must
accept `pnpm journeys --keep-going` to collect further test failures and consume
that option rather than pass it to Eichler's CLI. Infrastructure failures and
deadlines stop dispatch regardless of that option. Failure feedback appears when
observed, and the final result lists unrun work. Intentional early stopping must
be recorded explicitly by the parent invocation; a missing shard receipt alone
is never proof that dispatch was intentionally skipped. Catalog expectation
publication still requires the complete successful suite.

Everyday-use readiness requires a staged ramp from two to four to twelve actual
coding-agent sessions. Mac responsiveness is the priority during those sessions.
A twelve-request probe without twelve agent sessions does not satisfy this
requirement.

## Accepted command surface

The required validation command surface is a target, not a claim that every form
is implemented. The README records current routing support.

```sh
pnpm [run] test:surface <borrower-web|desk> [file selectors] [--grep PATTERN]
pnpm [run] validate surface <borrower-web|desk> [file selectors] [--grep PATTERN]
pnpm [run] journey <id> [--fault dropped] [--update]
pnpm [run] validate journey <id> [--fault dropped] [--update]
pnpm [run] journeys [--update]
pnpm [run] validate journeys [--update]
```

Journey IDs come from the submitted catalog. Profiles own private service startup,
readiness, teardown and evidence return. Stopped interactive journeys (`--at`)
remain outside this foreground validation contract. Unsupported selectors stop
with actionable feedback rather than silently broadening the test selection.
PostgreSQL and additional browser workflows can follow after these paths are
proven; they are not implicitly added by the heavy-test focus.

The routed Docker commands are:

```sh
docker build [-f RELATIVE_DOCKERFILE] -t TAG .
docker run --rm [-v "$PWD:CONTAINER_PATH[:ro]"] TAG [COMMAND [ARG...]]
docker image rm TAG
```

Docker forms run from the worktree root. A profile opts in and declares its
Dockerfile, permitted mount destinations, generated-output paths, runtime
configuration, resource limits, and deadlines. Parse argv rather than shell text.
Reject unsupported flags and conflicting options before submission, with the
rejected argument and a supported example when one exists. Preserve argument
boundaries, command overrides, stdout, stderr, command failure, and calling-shell
pipeline semantics.

The Docker grammar excludes detached or interactive runs, published ports,
privileged mode, host networking, host devices, Docker socket mounts, arbitrary
host mounts, external build contexts, registry pushes, and general Compose CLI
routing. Images must be built through Pandora. Arbitrary registry-image execution
is an extension.

## Images and source across calls

Pandora maps logical tags to remote image digests under a stable worktree identity.
Two worktrees can use the same logical tag without overwriting each other. A failed
rebuild preserves the previous mapping and reports that outcome. An unknown tag
fails with a build instruction. Image removal deletes the worktree mapping without
breaking an already admitted run or another worktree's mapping.

Build source and run source are distinct. Editing after `docker build` does not
change the image. A run without a mount uses the built image. A run with a
supported worktree mount captures current local files into a private remote
directory. The mount obscures image files at its destination, as a Docker bind
mount does. Pandora does not inject image dependencies into that directory.
Profiles that need dependencies at a mounted destination prepare them explicitly.

Feedback identifies the logical tag, worktree, run ID, image digest, and relevant
source digest. Moving a worktree must produce an explicit identity or recovery
outcome. It must not silently attach another worktree's state. Identity migration
is outside v0.1.

## Source, outputs, and failure evidence

Capture dirty tracked files and nonignored untracked files. Exclude credentials,
local dependencies, machine caches, and ignored files. These exclusions are not a
secret scanner. Apply the selected Dockerfile's ignore rules inside a supported
build snapshot. If an exclusion removes required input, report that limitation
before execution. v0.1 does not admit ignored inputs through profile configuration.
Opt-in ignored-input support requires a separate scope decision.

Record and verify a manifest of submitted bytes. Record the command, selectors,
source digest, runtime image, limits, and run ID. Each job gets its own writable
workspace, processes, and network environment. Shared caches require understood
concurrency and trust behavior. Execution containers never modify frozen
snapshots.

Retrieve available failure diagnostics after nonzero exit, timeout, or OOM. Keep
failed or partial outputs in the run artifact directory. Report delivery status
separately from the remote command result. Never report partial delivery as a
completed command. Print absolute local artifact paths and identify remote source
paths. Profiles define visible artifact retention and size limits. Artifact
delivery defaults to 2 GiB per invocation. Exceeding the configurable limit
preserves the remote result and stops automatic download and publication.
Raising the limit permits retrieval of the same result without remote execution.

## Tracked journey expectation return

An explicit `--update` authorizes automatic local return only to the selected
journeys' ledger fixtures and their entries in `packages/scenarios/fixtures/write-routes.json`.
The local declared files belong to that command while it runs: agents and users
must not simultaneously edit them. This is cooperative ownership, not filesystem
permission enforcement or a guarantee against arbitrary concurrent editors.

Preserve captured local dirty contents as the base. Before writing, verify complete
returned evidence and preflight every declared destination. Reject symlinks,
unsafe ancestors and undeclared changes. Preserve unrelated route-manifest keys;
never publish a focused run's incomplete manifest wholesale. A missing downloaded
artifact is an error, not a requested deletion.

Persist per-path base/target intent and recover interrupted publication without
remote rerun. Recognize exact already-applied targets, including additions and
explicit deletions. Other changed local contents are conflicts: preserve them and
return the proposed files/patch with usable paths. Retain original versions.
Changes to other input source remain stale; do not globally exempt fixture files
from source validation. Own recorded partial writes must not trigger the old
whole-source stale check before recovery.

Successful update output appears in ordinary `git diff`. The agent reviews it and
runs normal validation. Failed runs retain proposals as evidence; do not silently
publish partial successful shards from a failed catalog. Multi-file publication
is recoverable but not one atomic transaction. Interrupted or conflicting delivery
must not be reported as complete.

## Suite execution and aggregation

One agent command is one invocation with a frozen snapshot and an immutable list
of expected shard tasks. Use Eichler's global replay-cover and partition planner,
and Playwright's native sharding. Freeze catalog, manifest, weights, selection,
resource limits and task identities before dispatch. Keep each selected clean
journey and dropped-response replay together.

Each task has its own mutable workspace, services, execution identity and evidence
namespace. No concurrent shard may write a shared checkout. Aggregate exact
expected task membership and matching snapshot/plan identity; duplicate receipts
cannot stand in for missing tasks. Preserve journey statuses and distinguish
incomplete execution, test failure and missing cleanup from success.

For catalog updates, isolated tasks return proposals. One aggregation authority
merges only each task's explicitly owned journey entries and files. Reject
conflicting ownership and unexpected modifications. Deliver tracked updates only
after complete successful execution and verification. A lost worker is not proof
that its work stopped; do not automatically replace ambiguous executions.

## Tools, caches, and resource limits

Pandora uses SSH and rsync for transport, Docker for execution, and systemd for
independent supervision. Dependency preparation uses BuildKit with persistent pnpm
cache mounts. BuildKit and supporting services count toward worker CPU and RAM
limits. Bound preparation, service startup, execution, artifact collection, and
cleanup. Test containers do not receive unrestricted host Docker-socket access.

Keep dependency images separate from build outputs. A matching installation recipe
reuses its image. Changed installation inputs prepare a matching image under
admission limits and an independent deadline. Concurrent preparation for the same
key must deduplicate. The key includes toolchain, platform, recipe, lockfile,
package manifests, patches, and other installation inputs. Unsupported install
hooks fail clearly rather than reuse stale state.

Use the build tool's native cache for compilation. Each run keeps its own mutable
build directory and installed dependencies. Test invalidation across source,
dependencies, environment, toolchain, and platform changes. Capacity expansion
requires measured limits and does not automatically buy more worker capacity.

## Required acceptance evidence

Every scenario records command, snapshot or image identity, queue, preparation,
run, and transfer times, terminal result, cleanup, and returned evidence. Preserve
evaluator prompts and agent actions.

| Contract area | Required evidence |
| --- | --- |
| Familiar command | Codex and Opus use normal shell startup and separate calls; unrelated commands retain behavior |
| Frozen source | Dirty edits, new files, renames, and deletions produce the intended snapshot; ignored inputs stay excluded and report a required-input limitation; sibling worktrees stay excluded |
| Source mutation | Capture rejects inconsistency; later edits cannot alter accepted input or become a false current-source pass |
| Repair loop | An agent reads failure evidence, repairs local source, reruns, and obtains a result for the new bytes without coaching or fallback |
| Docker image lifecycle | Tags resolve across calls and launcher restart; mounted and unmounted source follow the stated semantics; same tags in two worktrees stay isolated; failed rebuild preserves the prior image |
| Dependency preparation | A missing image prepares automatically within limits; same-key preparation deduplicates; failure is observable and does not become a test failure or local fallback |
| Compiled build | Cold and identical builds plus source, dependency, and toolchain changes demonstrate invalidation and output return |
| Journey lifecycle | Services and mutable data are isolated; success, failure, cancellation, and worker loss have verified cleanup or an explicit unresolved record |
| Generated-output publication | Replaced and deleted generated files, retained prior generations, ignored destinations, unsafe paths, and interrupted delivery follow the ownership contract |
| Recovery | Client or SSH loss preserves the accepted run; retry recovers it without duplicate execution; changed source is stale |
| Admission and cancellation | Duplicate invocation reports existing work; configured FIFO/fair-turn policy holds; resource limits and timeouts hold; cancellation affects only owned resources |
| Sharded suites | Actual isolated shard runs aggregate complete membership, preserve replay assignments, reject duplicate/missing receipts and return named failure evidence |
| Tracked updates | Focused and catalog updates preserve unrelated entries, expose ordinary diffs, retain conflicts and recover interrupted delivery without remote rerun |
| Resource outcomes | Build OOM, test OOM, timeout, disk exhaustion, artifact limits, and missing terminal records have distinct actionable outcomes and never become false success |
| Unsupported Docker syntax | No submission or local execution occurs; feedback lets an agent select a supported form |
| Operating limit | A staged ramp at two, four, and twelve actual coding-agent sessions measures queue behavior and Mac responsiveness; a twelve-request probe alone is insufficient |

Scripted probes establish semantics before agent trials. Repair-loop trials use both
agent CLIs without prompts that supply a recovery strategy. A wrong-source pass,
lost output, duplicate execution, unannounced local fallback, or unverified
cleanup fails acceptance even when the launcher exits successfully.

## Deferred and optional extensions

The following are outside v0.1: general source writeback, mixed source/output
merging, detached services, cross-command forwarded ports, identity migration,
arbitrary registry images, arbitrary Docker and Compose routing, continuous sync,
multi-host scheduling, interactive previews, native macOS builds, universal
command routing, and replacement of target-repository CI.

Broader Docker compatibility and service-backed workflows beyond journeys are optional
extensions. [Issue #27](https://github.com/gbasin/pandora/issues/27) records the
operating-limit evidence. This contract does not claim that twelve-agent use is
ready.
