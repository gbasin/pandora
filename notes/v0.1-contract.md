# Pandora v0.1 command contract and evaluation

Design proposal, 2026-09-19. This document records the agreed scope and proposes
the detailed command grammar and acceptance criteria. It does not describe
implemented behavior. See the root README for the current SSH surface pilot.

## Agreed scope

Agents and worktrees remain on the dedicated Mac. Pandora routes configured
validation workflows and specific Docker command patterns to a Linux worker.
Profiles live outside the target repository. Other engineers need no changes.
Existing subscriptions and agent launchers remain in use.

The required coding loop is build, run/test, inspect evidence, edit locally,
and rerun. Separate shell calls must work. Include one service-backed validation
workflow before everyday use. Evaluate both Codex and Claude Opus.

Image tags are private to each worktree and survive launcher restarts. Commands
use frozen input snapshots. Declared outputs return automatically, with conflict
checks before local replacement. General source writeback is deferred.

Docker runs execute in the foreground. Validation owns the startup, readiness,
and cleanup of its supporting services. Detached services and forwarded preview
ports across commands are outside v0.1.

Unsupported Docker commands stop with actionable feedback inside routed
sessions. They never fall back locally. Local escape requires human control.
The executable wrapper is not OS enforcement: absolute paths and environment
changes can bypass it. No security or universal-interception claim follows.

Accepted runs finish within their deadline after client loss. Retry reconnects
to the same run. An active request is reported, never automatically replaced.

## Proposed command grammar

These forms are implementation targets, not commands supported by the pilot:

```sh
pnpm [run] test:surface borrower-web [file selectors]
pnpm [run] validate surface borrower-web [file selectors]
docker build [-f RELATIVE_DOCKERFILE] -t TAG .
docker run --rm [-v "$PWD:CONTAINER_PATH[:ro]"] TAG [COMMAND [ARG...]]
docker image rm TAG
```

The Docker forms initially run from the worktree root. A profile must opt in
and declare the Dockerfile, permitted mount destinations, output paths, runtime
configuration, and resource/deadline requirements. A service-backed workflow's
exact command and service recipe must be chosen from the target repository and
verified before implementation. Do not infer its semantics from its name.

Parse argv, not shell text. Reject unrecognized flags and conflicting options
before submission, with the rejected argument and a supported example where
one exists. Preserve argument boundaries, command overrides, stdout, stderr,
and command failure. Do not change the calling shell's pipeline semantics.

The initial Docker grammar excludes detached/interactive runs, published ports,
privileged mode, host networking, host devices, Docker socket mounts, arbitrary
host mounts, external build contexts, registry pushes, and general Compose CLI
routing. Add a pattern only with a specified meaning and evaluation coverage.
Docker read commands outside this grammar also receive actionable rejection;
do not return misleading local daemon state.

For a supported build, freeze the worktree and apply the selected Dockerfile's
Docker ignore rules within that snapshot. Explicit secret exclusions remain in
force. If exclusions remove a required input, report the limitation. Record the
snapshot, Dockerfile, builder, platform, and resolved base-image identities.

## Images and source across calls

Map logical tags to remote image digests under a stable worktree identity. Store
the mapping outside the launcher session. Two worktrees can both use app:test
without overwriting each other. Rebuilding a tag publishes its new digest only
after success; a failed build preserves the previous mapping and says so.

A run resolves and pins the digest when admitted. Later tag changes cannot
change a queued run. An unknown tag fails with a build instruction. Initial
support uses images built through Pandora; arbitrary registry-image execution
is a separate extension. Image removal deletes the worktree's mapping without
breaking an already accepted run or another worktree's reference.

Build source and run source are distinct. Editing after docker build does not
change the image. A run without a mount uses the built image. A run with the
supported worktree mount captures current local files into a private remote
directory. That mount obscures the image's files at its destination, as a Docker
bind mount does. Do not silently inject image dependencies into that directory.
Profiles needing dependencies there must prepare them explicitly.

The physical tag and worker path are implementation details. Feedback names the
logical tag, worktree, run ID, image digest, and relevant source digest. Moving a
worktree must produce an explicit identity/recovery outcome; do not silently
attach another worktree's state. Identity migration is not required for v0.1.

## Outputs and failure evidence

Profiles declare output roots and whether a path is a workspace output or a
diagnostic artifact. Restrict destinations to the owning worktree or Pandora's
artifact directory. Reject traversal and symlink escapes on both ends.

Always retrieve available failure diagnostics, including after nonzero exit,
timeout, or OOM. Publish build outputs into the workspace only after successful
execution and complete verified retrieval. Keep failed or partial outputs under
the run's artifact directory. Report that distinction with the exit status.

Capture destination state at submission, including ignored existing outputs.
Before promotion, compare local contents, existence, and file types against that
state. If they changed, preserve the local version and stage remote output as a
conflict artifact. Report a non-success delivery status separately from the
remote command result. Never present a conflict as a fully completed command.

Manifest checks cover files, deletions, modes, and allowed symlinks. Deletion is
limited to a declared output root and needs the same conflict check. Promotion
must guard against edits during comparison/replacement; an unchecked check-then-
copy sequence is insufficient. Specify and test the commit/recovery mechanism
before enabling automatic workspace writes. Interrupted transfers cannot leave
partially promoted output reported as complete.

Use one run ID in status, remote directories, local artifacts, and recovery
records. Print absolute local artifact paths. Keep raw logs and identify remote
source paths explicitly. Artifact retention and size limits belong to the
profile; reaching a limit must be visible, never a silent successful truncation.

## Tools, caches, and admission

Use SSH and rsync for transport, Docker for execution, and systemd for independent
supervision. Move dependency preparation to BuildKit with persistent pnpm cache
mounts. Compose can manage services from an external profile when needed.
Pandora owns routing, identities, lifecycle records, and output delivery.

Keep dependency images separate from build outputs. A matching installation
recipe reuses its existing image. Changed installation inputs automatically
prepare a matching image under admission limits and an independent deadline.
Deduplicate preparation for the same key. Include the toolchain, platform,
recipe, lockfile, package manifests, patches, and all installation inputs in the
key. Unsupported install hooks must fail clearly rather than reuse stale state.

Use the build tool's native cache for compilation. Eichler's Turbo tasks can
reuse declared outputs when invoked through Turbo; direct Vite/Playwright
commands do not gain that behavior merely from mounting a Turbo cache. Evaluate
compiler-specific caches only for workloads that need them. Each run keeps its
own mutable build directory and installed dependencies. Share only caches whose
concurrency and trust requirements are understood. Test invalidation across
source, dependencies, environment, toolchain, and platform changes.

BuildKit and supporting services count toward the worker's CPU/RAM budget.
Bound preparation, service startup, execution, artifact collection, and cleanup.
Do not grant a test container unrestricted access to the host Docker socket.
Select resource limits from measurements, including cold builds and concurrent
service memory. A worker busy with long compilation cannot promise short queue
times. Capacity expansion remains explicit, with no automatic paid burst.

## Evaluation matrix

Every scenario records command, snapshot/image identity, queue/preparation/run/
transfer times, memory peak, terminal result, cleanup, and returned evidence.
Preserve evaluator prompts and agent actions so interventions remain visible.

| Story | Evidence required |
| --- | --- |
| Familiar command in Codex and Opus | Routing works with normal shell startup, PATH additions, and separate shell calls; unrelated commands retain behavior |
| Dirty source and nested worktrees | Edits, new files, renames, deletions, and ignored declared inputs reach the correct snapshot; sibling Git worktrees stay excluded |
| Edit during capture or execution | Capture detects inconsistency; later edits never change accepted input or become falsely reported as tested |
| Seeded bug and repair | Agent reads returned failure evidence, fixes local code, reruns, and obtains a result for the new bytes without human coaching |
| Build then run | A tag resolves across calls and launcher restart; image source and mounted current source behave as specified |
| Two worktrees, same tag | Different builds and outputs remain separate; failed rebuild preserves the old mapping visibly |
| Warm compiled build | Compare cold build, identical rerun, one-file edit, dependency change, and toolchain change; verify both speed and invalidation |
| Missing dependency image | Preparation is automatic, bounded, deduplicated, and observable; failure does not become a test failure or local fallback |
| Required service-backed validation | Readiness works; services and mutable data are isolated; success, failure, cancellation, and worker loss have verified cleanup |
| Output return | New/replaced/deleted outputs and ignored destinations behave correctly; concurrent local edits are preserved; unsafe paths are rejected |
| Interrupted artifact promotion | Retry recovers the same result without duplicate execution or partially reported success |
| Client/SSH loss and retry | Existing work finishes within its deadline; same-run recovery works; changed source is labeled stale |
| Queues and cancellation | Duplicate invocation reports existing work; agents keep waiting; cancellation affects only owned resources |
| Resource failures | Build OOM, test OOM, timeout, disk exhaustion, and missing terminal records produce distinct actionable outcomes |
| Unsupported Docker syntax | No submission or local execution; feedback lets an agent choose a supported form without repeated bypass attempts |
| Parallel coding loops | Increase from two to four, then twelve agents only as capacity permits; measure queue fairness and Mac responsiveness |

Scripted probes establish semantics before agent trials. Run real repair loops
with both agent CLIs and without prompts that supply the required recovery
strategy. A blocked agent, repeated restart, local fallback, wrong-source pass,
lost output, or human intervention is an evaluation failure even if the launcher
exits successfully. Record all trials, including failures.

The existing surface pilot provides recovery and four-agent contention evidence.
It does not establish Docker routing, compiled-build cache performance, service
lifecycle, safe output promotion, or readiness for everyday use. Final operating
limits and retention values require measurements. CI remains independently
required. Multi-host scheduling, continuous sync, general source writeback,
interactive previews, native macOS builds, and universal command routing remain
outside this v0.1 proposal.
