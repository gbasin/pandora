# Turbo's remote cache on the worker, 2026-09-22

v0.2 ships an HTTP remote cache that turbo already knows how to talk to, served
by the worker to its own runs. It replaces the mounted per-repository cache
directory from `bc6bd5b`. Everything below was measured on `ubuntu@WORKER`
(4 vCPU AMD EPYC-Milan, 15.6 GiB) between 22:20 and 23:50 UTC, with eichler's
`pnpm check` as the workload.

Branch `v0.2/assembly`, commit `892424f`. `pandora/engine/turbocache.py` (≈480
lines, stdlib only) and `pandora/tests/test_turbocache.py` (19 tests over real
HTTP on loopback).

## What it is

| Piece | Choice | Why |
|---|---|---|
| Protocol | Vercel's: `GET /v8/artifacts/status`, `HEAD/GET/PUT /v8/artifacts/{hash}`, `POST /v8/artifacts` (query), `POST /v8/artifacts/events` (200, dropped) | what `turbo run` speaks; nothing to install in the golden |
| Auth | `Authorization: Bearer <token>`; 401 otherwise | the token is a random per-worker value in `<engine>/turbo-cache/token` (0600), made on first use. It is not a user secret: it stops a process on the bridge that was not handed one from writing what the next run replays |
| Namespace 1: repository | a path prefix, `TURBO_API=http://10.141.0.1:4199/r/<repo>` | turbo appends `/v8/artifacts/...` to whatever `TURBO_API` is, verbatim -- verified on the worker, first try. The repository travels in every URL and turbo never knows |
| Namespace 2: team slug | `TURBO_TEAM=linux` for runs | turbo's hash does **not** cover the OS: the Mac's local runs and the worker's remote runs produced identical task hashes all day (`@eichler/domain:typecheck` is `49fad75c54905a3f` on both). A darwin artefact replayed on linux is a wrong answer. CI joins as its own slug in v0.3 |
| Storage | one file per entry, `<engine>/turbo-cache/store/<repo>/<slug>/<hash>`: 4-byte header length, JSON header (tag, duration), body | one `os.replace` per write, so concurrent writers of one hash each land a whole entry; never a body from one and headers from the other |
| Bound | `max_mib` file beside it, default 4096; oldest-mtime first down to 90 % whenever a write crosses it; a hit bumps mtime; one artefact over a quarter of the bound is 413 | on the host disk (23 GiB free), not the pool |
| Where it listens | the runs' bridge address only (`pandorabr0`, 10.141.0.1:4199) | reachable from every instance with no firewall change; not from the internet |
| How it runs | the engine's user unit, `pandora-engine.service`, now `Type=simple`: the boot reconcile is its `ExecStartPre`, the server its `ExecStart`, `Restart=always` | "part of the engine service", one unit, linger already on. `provision` writes it; `bin/engine-serve` runs it from the newest shipped bundle |
| Local cache in a run | **off**: `TURBO_CACHE=remote:rw` | a run's local cache lives in an instance destroyed when the run ends. Writing it is a second copy of every artefact that nothing will read. Within one run, turbo reads the remote for anything it just wrote |
| When the server is down | the run starts without `TURBO_*` and says `turbo cache off: <reason>` | probed with a 1 s TCP connect before the command; a cache is a speed, never a verdict |
| Telemetry | `TURBO_TELEMETRY_DISABLED=1` | otherwise a POST to vercel.com from inside every run |
| CLI | `pandora cache stats`, `pandora cache clear [--repo R]` | over the engine link; stats reads the disk and asks the live server for its counters |

## The mounted directory from `bc6bd5b`: replaced

| | Mounted dir (`bc6bd5b`) | HTTP server |
|---|---|---|
| per-run cost | an `incus config device add ... shift=true` (idmapped mount) per run | one 1 s-bounded TCP probe |
| bound / eviction | none; grows forever | LRU to a byte bound |
| clear, stats | `rm -rf` by hand | `pandora cache clear/stats` |
| concurrent writers | turbo's own local-cache writes, two instances, one directory, through an idmapped mount -- never measured | atomic replace, measured below |
| CI (v0.3) | cannot reach it | same protocol turbo uses against Vercel; a new slug and a route |
| namespacing by OS | the directory name | the slug, enforced by the server |

`attach_cache` is gone from the executor interface, the Incus driver and both
test fakes, and the worker's old `~/pandora-engine/cache/` directory (772 KiB)
was deleted.

|---|---|---|

| 2 | a cold `pnpm check` populates | after `pandora cache clear`: `Cached: 0 cached, 15 total`, 80 s caller wall; the store then held the run's entries |
| 3 | a second run **from a different clone** hits | a fresh `git worktree add` of the same commit (`pandora-measure-2`): **`Cached: 15 cached, 15 total`**, 22.1 s wall |
| 4 | two concurrent writers of one hash | cache cleared, then `pnpm check` from two worktrees at once, both cold, sharing 6 of 15 task hashes: **both passed**; server counted 26 PUTs for 24 entries (two hashes written by both), 4 hits, 0 errors, 0 tracebacks in the unit's journal. Unit test: six simultaneous PUTs of 300 kB to one hash, all 202, the survivor byte-identical to one of them, no temp files left |
| 5 | a server restart keeps entries | `systemctl --user restart pandora-engine`: 24 entries before, 24 after; the next `pnpm check` **15 cached, 15 total**, 20.3 s wall |
| 6 | clear works | `pandora cache clear --repo eichler` → `cleared eichler: 33 entries, 0.6 MiB`; `stats` → 0 entries |
| 7 | the server being down costs speed only | unit test: no `endpoint.json` → run passes, `TURBO_API` absent, evidence `turbo_cache.error = "no cache server has started on this worker"` |

`pandora cache stats` after a day of eichler checks:

    turbo cache  0.6 of 4096 MiB, 33 entries; server 10.141.0.1:4199
      eichler/linux                33 entries       0.6 MiB
      since start: 87 hits, 33 misses (72% hit), 33 puts, 0 evictions

**The cache is tiny for this workload.** eichler's `check` caches only
`typecheck`, which has no outputs -- an entry is a replayed log. 33 entries are
0.6 MiB. The 4 GiB bound is for `build` and `test` tasks with real outputs;
nothing measured today comes near it.

## What it buys

A fully cached `typecheck` inside a remote `check` is 0.1 s against 45.6 s cold
at `--concurrency=2`. The rest of a warm `check` is not turbo's: format, lint,
docs, the design vitest and the node tests run every time, which is why a warm
remote `check` still executes for 11-12 s. See the check profile note.

## Found on the way

**turbo 2.10's "shared worktree cache".** On the Mac, turbo detects git
worktrees and uses the *main* checkout's cache directory for every worktree
(`Remote caching disabled, using shared worktree cache`). That is why the three
local runs at the start of this session were already warm. It matters for the
local measurements: they set `TURBO_CACHE_DIR` to a directory of their own so
that "cold" meant cold without wiping a cache every other agent on this Mac
shares.

**turbo closes the events POST without reading the answer.** The first server
logged a `BrokenPipeError` traceback per run. `Server.handle_error` now drops
broken pipes and resets silently.

**A new bundle does not restart the server.** The unit runs the newest bundle
present when it starts. A client that ships a newer engine gets the new runner
immediately (every supervisor is a fresh process) but the old cache server until
the unit restarts; `pandora worker provision` restarts it when the unit file
changes. The protocol is stable enough that this has not mattered.

## Recommendations

1. **Keep remote-only in runs.** Nothing measured argues for a local cache in an
   instance that is deleted at the end of the run.
2. **CI in v0.3 is a route and a slug, not a new server:** expose the same
   server through the existing SSH link or a tunnel, give CI `TURBO_TEAM=ci-linux`
   (or reuse `linux` deliberately -- CI's linux artefacts *are* valid for runs,
   which is the point of sharing). Do not let the Mac write `linux`.
3. **Size the bound when a job caches real outputs.** Today's 0.6 MiB says
   nothing about `pnpm test` or `build`.
4. **Restart the server on bundle change** if the protocol ever changes: the
   runner already knows the bundle digest; comparing it to the server's
   `endpoint.json` is five lines.
