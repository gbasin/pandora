## Feature 1: one automatic remote retry

### The rules, in the order `Daemon.retry_verdict` applies them

1. Only `outcome == infra_failed`. `oom`, `timed_out`, `cancelled` and
   `command_failed` never reach the table.
2. Once. The retry is never retried.
3. Never a cancelled run, never a stale one (`cli_exit` 75).
4. **Never once any of the command's own output reached the caller.** The
   daemon watches every streamed line; a line that is not `pandora: ...`
   (optionally under fan-out labels like `[1/2] `) and not blank is output, and
   marks `runs/<id>/command-output`, so a restarted daemon also knows. An
   unterminated fragment counts as soon as it can no longer become a
   `pandora:` line (`could_be_pandora`), because a restart could lose its
   newline.
5. Only a cause the table marks retryable.
6. Write-back: allowed when the first four hold, because the failed attempt is
   never delivered, so its proposal is never fetched or settled. The retry
   freezes nothing new. Its proposal is fetched from the retry's own attempt
   (`run.remote` has moved to it) and settled against the hashes `serve_run`
   saved before `accepted`, which are the same input's. When the daemon cannot
   read how write-back is armed -- `plan['options']` is not a dict, or an
   adopted run's argv has `--update` and its plan is gone -- it does not retry,
   and says so. `plan['options']['update']` is read, never restructured.

The retry is `worker.resubmit`, remote to remote. A refusal (`admission-refused`,
`disk-floor`, `source-gone`, an unreachable worker) ends the run at exit 70 with
`pandora: the retry could not be submitted (...)`. **Nothing on this path can
reach `serve_local`**: `fall_back` is only called from `serve_run`, before
`accepted`, and a test asserts the job's marker file never appears.

A lost connection is not an infra verdict and never retries. After six failed
`follow` attempts the run may still be executing, so resubmitting would run it
twice (`worker-lost` in the table).

### The cause table

| Cause | Raised by | Retry | Why |
|---|---|---|---|
| `clone-failed` | `CloneFailed` in `supervise` | **yes** | a clone of an existing golden is cheap and independent of the failed one |
| `instance-lost` | `InstanceLost`, executor outcome `lost` | **yes** | a fresh instance shares nothing with the one that vanished |
| `execution-failed` | `ExecutionFailed` (inject, `incus exec`, synthetic git) | **yes** | the host could not start or feed the command |
| `supervisor-gone` | `reconcile` after an engine restart | **yes** | says nothing about the input |
| `prepare-failed` | `PrepareFailed` | no | a golden that failed to build fails again, and a second build costs minutes |
| `disk-quota` | `CloneFailed` naming the disk quota | no | a resource verdict: the same quota refuses again |
| `destroy-incomplete` | a pass whose instance survived destroy | no | the command reached a verdict; the leftover machine is the operator's |
| `partition-unverified` | fan-out verification | no | the shards ran; their report against the plan will not change |
| `shard-failed` | fan-out, worst child `infra_failed` | no | the shard already had its own retry |
| `admission-timeout` | fan-out child never admitted in 30 min | no | a retry joins the same full queue |
| `engine-error` | any other exception | no | an unrecognised failure is not retried |
| `disk-floor`, `admission-refused` | `submit` | n/a | before `accepted`; the fallback policy owns them |
| `worker-lost` | the daemon, `follow` failed six times | no | the run may still be executing |

`prepare-failed` is the judgement call. A golden build can fail on a transient
apt mirror, but it costs minutes, and a deterministic failure retried is minutes
more for the same exit 70. It is one line in `CAUSES` to flip.

### Sharded runs: one shard retries alone

Chosen because the fan-out makes it natural and the whole-run alternative is
nearly always forbidden. The parent already owns each child's lifecycle and
admits children one at a time, so a retried shard is one more `start_child` +
`admit_and_spawn` with request suffix `shard:<i>:retry` and `retry_of` set. Its
siblings' verdicts stand. A whole-run retry would re-run shards that passed,
and since shard output streams to the caller as it appears, rule 4 would
refuse it anyway once any sibling had printed.

The per-shard rule is the same rule applied to the shard: retryable cause, the
shard's own log holds no command output, parent not cancelled, once. The
daemon's whole-run retry still applies to a parent that failed before any
output (the plan step's clone failed, say), and refuses `shard-failed`.

### What records it

* the run log: `pandora: infrastructure failure before output (clone-failed); retrying once`
* `meta.json`: `attempts` (earlier attempts), `remote` (the current one)
* `result.json` and `pandora result <id> --json`: `attempts` (every attempt: remote, outcome, cause, exit, wall), `retry: {retried, of, cause}` or `retry: {retried: false, cause, why}`
* the engine ledger: the retry's row has `retry_of`; its `request_id` is `<caller id>:<job>:retry`
* a fan-out result: `evidence.shard_retries`, and `retried_from`/`retry_cause` on the shard row
* `pandora stats`: `infra retries: 1 run(s), 1 recovered (clone-failed x1)`

The hint names both attempts on a second failure:

    pandora: hint: infrastructure failed on both attempts: r1a2... (clone-failed), then r9f0... (instance-lost); neither reached a verdict, so this is not a test result -- check the worker with pandora stats

and says why when it did not retry:

    pandora: hint: infrastructure failure (instance-lost) was not retried: the command's own output had already reached you, and a partly observed run is not repeatable; nothing reached a verdict

## Feature 2: flaky pairs

**The rule.** When a whole run reaches a verdict (`passed` or
`command_failed`), `history.previous_verdict` finds the most recent earlier
verdict with the same repository, job and input digest -- the `same_input_as`
key -- **and** the same argv, environment and cwd. If the two disagree, the pair
is recorded: `result.flaky = {with, order, failed, failed_run, passed,
passed_run}` and `flaky_with` on the later row. `infra_failed` attempts are not
verdicts and are skipped, so a retry between the two does not break the pair.

**Per shard** when both runs are fan-outs cut into the same shard count: shard
`i` of this run against shard `i` of the previous one, the last attempt at each
index. This fires even when both parents failed on account of another shard.

**No drift.** A remote input is a frozen snapshot, so a remote run cannot
drift; the rule refuses a result that says `drifted` anyway. The local lane has
no `input_id` ledger and is not compared.

**Evidence only.** Nothing re-runs. The hint:

    pandora: hint: this input failed then passed with no change; treat as flaky, see pandora result 3fa91c0d2e11
    pandora: hint: shard 2/4 of this input failed then passed with no change; treat as flaky, see pandora result 3fa91c0d2e11

`<failed-id>` is the caller-visible id, the first segment of the failed
attempt's request id. `pandora stats` counts pairs in its window (`flaky: 1 run
pair(s), 2 shard pair(s) failed and passed on one input`); a pair is recorded on
its later attempt only, so counting results counts pairs.

## Feature 3: progress lines

Estimates are the median of the last **5** same-job verdicts (`passed` or
`command_failed`), in the same role (a shard against shards), and are omitted
below **3** samples, which is admission's cold-start threshold for the same
reason. The engine reads its ledger; the client reads its own `runs/`.

### Catalogue

| Line | Said by | When | Estimate |
|---|---|---|---|
| `pandora: syncing 4,912 files, 375 MiB` | client, `worker.submit` via `Heartbeat.say`, before `accepted` | a source-cache miss, just before rsync | none. The size is the tree's, not the wire's: `--link-dest` sends only what the cache lacks |
| `pandora: instance ready in 3.1 s` | engine, `runner.supervise` | after harden | a measurement; also recorded as `durations.boot` |
| `pandora: running (typical 4m10s for check; cpus hint 2)` | engine | just before the command | engine ledger `durations.execute`. Replaces the old `pandora: cpus hint 2` line, so it adds no line |
| `pandora: shard 2/4 queued behind 1 run, ~40 s` | engine, `fanout.admit_and_spawn` | first refused admission | soonest live run's median wall minus its elapsed time |
| `pandora: shard 2/4 still queued behind 1 run` | engine | at most every 60 s after that | none |
| `pandora: queued behind 1 run, ~40 s` | client, `Budget.admit` (local lane) | first wait | the same, from local history |
| `pandora: still queued behind 1 run` | client | at most every 60 s | none |
| `pandora: infrastructure failure before output (<cause>); retrying once` | daemon | on a retry | |
| `pandora: shard 2/4: infrastructure failure before output (<cause>); retrying once` | engine fan-out | on a shard retry | |
| `pandora: run 3fa9... is running on the worker as r1a2... (1m20s since accepted; typical 4m10s for check)` | `pandora wait <id>`, once on attach | from the `phase` field on the attach frame | client history |

A plain remote run has **no queue line**, because the engine admits or refuses
and never queues a single run (see `stats.py`'s docstring). A refusal goes to
the fallback policy before `accepted`. Queues exist for fan-out children and for
the local lane, and those are the two that speak.

`pandora wait` replays the log from byte 0, so the phase line is printed before
the replay. It rides on the `accepted` frame rather than in the stream, because
the stream is the run log byte for byte and a client resumes by offset into it.

## Found in the existing code

* **The remote lane sent the engine's `pandora:` lines to stdout.** `Run.stream_in`
  framed every remote chunk as `out`, so `pandora: turbo cache ...` and
  `pandora: cpus hint 2` reached the caller's stdout, against `--help`'s
  "Pandora's own lines go to stderr". Fixed: split by line; a held fragment is
  not acknowledged in `remote-offset`, so a crash replays it.
* **The fan-out printed `waiting for a lane` every two seconds** while a child
  waited for admission. Now once, then at most once a minute.
* **A passing shard could be reported `infra_failed`, intermittently.** The
  parent's `poll` read a row marked `finished` before `write_result` had written
  `result.json`, or while `supervise` was rewriting it with `learned`, and
  called it "no result file" or a JSON error. Reproduced 1 in ~40 under load
  once this work widened the window. Fixed: result files are replaced whole
  (`runner.write_json`), and a missing file gets a 10 s grace.
* **`same_input_as` ignores argv.** `journey S0-01` and `journey S0-02` from one
  tree are "the same input". Proof 2 of the slice note reads it as a cache-hit
  identity. The flaky rule compares argv, environment and cwd as well.
* **The ledger's docstring said a retry needs no migration.** `request_id` is
  `UNIQUE`, so a second attempt at one request cannot exist; the retry is a
  second request with `retry_of`.
* **A resumed run's `started` was reset to the restart time**, which made its
  `queue_ms` wrong. `resume_interrupted` now keeps the recorded value.
* `pandora logs` still writes both streams to stdout. Unchanged.

## Unverified

* **No live worker run.** `resubmit` has never run on the worker; the source
  cache path check, the admission of a retry beside a live run, and the real
  Incus error strings behind each cause are all untested there.
* The per-shard retry has run only against the fake executor.
* The stdout/stderr split has not seen real engine output. A command that
  itself prints lines beginning `pandora: ` now has those lines on stderr.
* `syncing ...` costs one `stat` per manifest file on a cache miss. Eichler's
  ~4,900 files were not measured.
* The estimates' accuracy: no ledger with real history was read.
* A retried `--update` run. Write-back landed on `v0.2/assembly` while this
  work was in flight, and the combination is unit-tested through
  `retry_verdict` only. No test runs a retried write-back end to end.

## A stash shared across worktrees

`git stash` is per repository, not per worktree. A `git stash; ...; git stash
pop` here, used for a baseline test run, popped the write-back agent's stash
(`WIP on v0.2/writeback`) into this worktree instead of mine. This worktree was
reset and its own stash applied by SHA. By then the write-back entry had
already left the stash list, taken by its owner. Nothing was lost here. Other
agents sharing this repository should not use `git stash`.
