# Tier-2 sharding, proved on eichler's surface suite, 2026-09-22

`pnpm test:surface desk` typed in an Eichler worktree now builds once on the
Linux worker, cuts the 302-test suite N ways, runs the shards in N independent
Incus instances, and refuses to report a pass unless the test ids the shards
observed are exactly the partition the plan named. Four shards take **250 s**
where one takes **510 s**.

Branch `v0.2/assembly`, commits `ed040a5` and `303ab52`. Everything measured on
`ubuntu@WORKER` (4 vCPU, 15.6 GiB, Incus 6.0.5) between 03:40 and 04:35
UTC on 2026-09-22.

### The configuration

```toml
[jobs.shards]
strategy = "argv"                       # or "env"
template = "--shard={i}/{n}"            # argv strategy; env = { … } for the other
default = 2
max = 8
plan = ["node", "tools/validation/surface-runner.mjs", "plan", "{args}",
        "--build", "--shards", "{n}", "--out", "{plan}"]
expect_flag = "--expect"
report = "apps/*/test-results/surface-run-{i}-of-{n}.json"
plan_outputs = ["apps/desk/dist", "apps/desk/e2e/dist",
                "apps/borrower-web/dist", "apps/borrower-web/e2e/dist"]
```

Unknown keys are refused with the allowed set printed beside them, as everywhere
else in the loader. Four refusals are specific to this table and each exists
because the alternative is a lie:

* `plan` without `report` — an inventory nothing is checked against is
  decoration, so Pandora will not accept one.
* `report`, `expect_flag` or `plan_outputs` without `plan` — there is nothing
  for them to refer to.
* a `template` missing `{i}` or `{n}` — a shard flag that cannot say which shard.
* a sharded job with no `artifacts` output — the report would have no way home.

`strategy = "argv"` appends the rendered template; `strategy = "env"` sets named
variables. Both also get `PANDORA_SHARD_INDEX` and `PANDORA_SHARD_TOTAL`, so a
runner that likes neither spelling still has the pair. The shard count is
overridden by `PANDORA_SHARDS` from the shim, never by parsing `--shards` out of
the command line: that flag belongs to the repository's runner and Pandora does
not read the repository's command line.

### The parent

A parent attempt runs no command, holds no memory reservation and occupies no
CPU lane. It owns instances only through its children, and `Scheduler.live_rows`
excludes it for exactly that reason. The sequence:

    plan (tier 2)   one instance: build once, list the partition, write plan.json
      collect       plan.json and `plan_outputs`, pulled onto the host
    decide N        default, then PANDORA_SHARDS, then max, then free lanes
    dispatch        N children, each admitted separately, each its own clone,
                    each grafted with what the plan built
      drain         a failure stops *new* dispatch; what is running finishes
    aggregate       every report, checked against the planned partition
      merge         one artifact tree; disagreements kept, not resolved
    verdict

Every child is admitted on its own rather than the parent reserving the whole
fan-out up front. A parent holding four reservations while using one would
starve another repository, and would deadlock the moment the box could fit three
of its four shards.

## Verified and unverified

A tier-2 result carries a `verification` block and is `verified: true` only when
all four hold:

* every dispatched shard filed a report — **a missing report is never scored as
  zero failures**, which is the single rule the aggregator exists for;
* each shard's observed ids equal its planned ids as a set;
* no test ran in two shards;
* no test was planned and never observed, and none was observed that was never
  planned.

A tier-1 job has no plan, so nothing describes the partition. Its result says
`verified: false, unverified: true` with the reason *"this job declares no plan
step, so nothing describes the partition"*. That is not a soft pass: it is the
honest statement that a green `--shard=2/4` proves something ran and never that
four shards between them covered the suite. A caller who wants the receipt adds
a `plan`; a caller who does not gets the speed and is told what they gave up.

Output collisions are the third verdict. Identical bytes at one path across
shards are expected and ignored. Differing bytes are a collision: every version
is retained under `.pandora-shards/shard-<i>/<path>`, the merged tree keeps the
lowest shard's, and the run exits **75** rather than handing back a tree that
silently kept whichever shard finished last.

## Numbers

Desk surface suite, 302 tests, `SURFACE_WORKERS=1` so one shard is one browser
and the comparison measures the fan-out rather than Playwright's own pool.

| N | wall (caller) | plan | slowest shard execute | fastest | per-shard peak MiB | speed-up |
|---|---|---|---|---|---|---|
| 1 | **510 s** | 11.9 s | 489.8 s | — | 2,523 | 1.00x |
| 2 | **304 s** | 12.6 s | 283.5 s | 278.6 s | 2,481 / 2,388 | 1.68x |
| 4 | **253 s** | 16.1 s | 225.1 s | 173.1 s | 2,403 / 2,328 / 2,384 / 2,244 | 2.02x |

Four shards on four vCPU is where it stops paying: the slowest shard (225 s) is
1.3x the fastest (173 s), and the box is the constraint rather than the
partition. The plan step's own cost grows with N because it lists the selection
once per shard plus once for the whole; at N=4 that is 16 s of the 253 s.

Per-child costs, from the N=4 run:

| Step | Cost |
|---|---|
| clone from the golden | 0.06–0.33 s |
| start and become ready | 0.26 s |
| inject the source (`device-rsync`, cache hit) | 0.79–1.05 s |
| graft the plan's build (`device-rsync-over`) | **0.22–0.78 s** |
| harden | 0.02 s |
| destroy | 0.93 s |

**Snapshot-of-parent versus re-inject, measured directly.** Taking a snapshot of
the *running* plan instance and copying children from it costs 0.08 s for the
snapshot, 0.11 s per copy and 0.26 s per start — about **0.4 s per child**
against the **1.3–2.4 s** the implemented path costs. So the snapshot does win,
by roughly a second a child, which on a 250 s run is under half a percent. It is
not taken, for a reason worth more than the second: a child copied from the plan
instance inherits everything else that instance did — a dirty `/tmp`, a started
dockerd, whatever the build left behind — and the property that makes a shard
reproducible is that it starts from the same golden every other run starts from.
The measurement is recorded so the trade can be revisited if the build-once
tree ever gets large enough for the second to matter.

by a guess about how Playwright cuts.

## The CPU hint, closed and not quite closed

The slice left `PANDORA_CPUS` frozen at admission, which made proof 7 of that
note tell two runs on a four-core box that they had four cores and two. It is
now recomputed under the admission lock in the last moment before the command
starts (`runner.cpus_now`), and proof row 8 shows N=2 giving both shards 2.

At N=4 the first shard got **2** and the other three got 1. That is not a bug
and it is not fixed either: shard 1's command had already started when shards 3
and 4 were admitted, and the environment of a started process cannot be
rewritten. Closing the remaining window needs the thing the slice note named —
a hint the runner re-reads from a file — rather than a better moment to set an
environment variable. The error is now bounded by how long dispatch takes
(~1 s per child) instead of by the whole run.

## Gaps

1. **Paths cannot name the app.** `plan_outputs` and `outputs` list both
   `apps/desk` and `apps/borrower-web` because the loader has no `{p.app}`
   templating (it is in the contract draft, §3.8). The run therefore reports
   three declared outputs missing on every desk run. Cosmetic, and the fix is
   the templating, not a special case.
2. **The build-once tree is not collision-checked.** Each shard's Playwright run
   writes screenshots into `apps/desk/e2e/dist/artifacts/`, which is a
   `plan_outputs` directory rather than an `artifacts` one, so those files never
   come home and never reach `merge_outputs`. Verified harmless here — every
   file the plan produced was present and byte-identical in both shards of the
   N=2 run — but a suite whose shards wrote *conflicting* files there would not
   be caught.
3. **A collision has never been seen in the wild.** Exit 75 and the retained
   `.pandora-shards/` tree are covered by a unit test and by nothing on the
   worker; 0 collisions across 6 real fan-outs.
4. **`--keep-going` is untested end to end.** The flag is read from
   `PANDORA_KEEP_GOING` and the drain path is exercised by unit tests, but no
   worker run has had a shard fail while others were still pending.
5. **`install_command` can succeed wrongly**, as above. A golden should assert
   what it contains: a `[worker] verify` command whose non-zero exit fails the
   build would have caught the missing browsers in 64 s instead of an hour.
6. **`SURFACE_WORKERS` is pinned to 1 in the configuration** rather than
   following `PANDORA_CPUS`, because the environment table cannot reference
   another variable. It made the N table clean; it also means the configuration
   is not what a single-instance caller would want.
7. **Tier 1 is unproved on the worker.** It shares the code path and has unit
   tests, but the journey job's env-matrix sharding has not been run remotely.
8. **Two goldens with overlapping toolchains.** The surfaces golden and the
   journey golden differ in `service_images` and `install_command` and each costs
   ~3-5 GB. A pool of 18 GiB will not hold many more; golden GC is still POC
   blocker 3, untouched.
9. **The plan step lists N+1 times.** 11.9 s at N=1 and 16.1 s at N=4. The
   runner could list once and partition in memory, which is an Eichler change
   rather than a Pandora one.
10. **No local browser suites were run on this Mac deliberately** — but one was
    run by accident, when the first shim invocation fell back locally because
    the worker's pre-sharding ledger refused the submission (fixed in
    `303ab52`). 302 tests, 3.3 minutes, on the Mac. That number is the only
    local data point here and is not a baseline anyone should use.
