## 1. Why `check` needs git and journeys did not

`pnpm check` is `pnpm validate check` -> `tools/validate.mjs`, which calls
`fingerprint(root)` (`tools/validation/state.mjs`) unconditionally: `git
rev-parse HEAD`, `git diff HEAD --binary`, `git ls-files --others`. Then the
docs half runs `check-markdown-status.mjs` and `check-tracked-captures.mjs`,
both over `git ls-files`. `pnpm journey` is `node
tools/validation/journey-runner.mjs run` directly -- it never reaches
`validate.mjs`, so it never asked git anything. That is the whole difference.

### (a) or (b)

| | (a) synthetic repo in the run | (b) bare mirror on the worker, alternates + gitfile |
|---|---|---|
| worker disk | none that outlives the run (~300 MiB of loose objects inside the instance, destroyed with it) | eichler's `.git` is **2.0 GiB** (1.82 GiB pack, 196k objects) per repository, plus GC |
| first use | nothing | 1.8 GiB over the Mac's link, or a GitHub credential on the worker for `git fetch origin` -- a secret the worker does not hold today |
| per run | **2.9-3.6 s** (`git add -A` of 4,961 files / 375 MiB with loose compression off, 0.1 s commit) | a push of unpushed commits over SSH (~1 s), then an index built from `HEAD` whose stat data cannot match files injected on another machine, so the first `git diff` re-hashes the tree anyway (~0.6-1 s measured with `--info-only`) |
| moving parts | one shell script in the driver, two path lists from the client | a scheduled fetch, a push path, alternates, a gitfile, GC, a credential |
| history | none | real |

**Chosen: (a).** Nothing `check` or `native-unit` runs needs history, and (b)
costs a credential, 2 GiB and a scheduler to save ~1.5 s. It is declared per
job (`git = "synthetic"`), because a journey pays 3 s for nothing.

What (a) does that the obvious stub did not: the index is **this worktree's
tracked set**, not `git add -A`. The client's freeze marks the exceptions --
untracked files (`git ls-files --others --exclude-standard`) and tracked files
matching an ignore rule (`--cached --ignored`) -- and the driver removes the
first from the index and force-adds the second. The stub that `8d5ec5f` swept
into the example config ran `git add -A`; it would have made every untracked
scratch note an agent left in `notes/` "tracked", and `check-markdown-status`
would then fail on the worker for a note it never reads on the Mac.

The commit has a fixed author, date and message, so equal inputs have an equal
`HEAD` (verified twice on the worker: `ac0ee821...` both times).

**Checks that would get a wrong answer from (a)** -- none of them in `check` or
`native-unit` today:

* anything comparing to a ref -- `git merge-base`, `origin/main`, `turbo
  --affected`, `git log`, `git blame` -- sees one root commit and no remote;
* anything that reads the real commit id: `git rev-parse HEAD` is the synthetic
  one (eichler's fingerprint is only compared with itself inside one run, so it
  is unaffected);
* anything distinguishing staged from unstaged: both are in the commit, `git diff
  HEAD` is empty;
* `tools/codex-pr-report/*`, `tools/progress/*` and `tools/proj.mjs` all shell
  out to git with history in mind. They are not claimed. If one is ever claimed,
  it is the job that should say `git = "mirror"`, and that is when (b) earns
  its cost.

Measured `git add -A` variants on the worker, in a clone of the golden:

| loose-object compression | `git add -A` | commit | eichler fingerprint afterwards |
|---|---|---|---|
| git default (zlib -1) | 9.13 s | 0.13 s | 25 ms |
| `core.looseCompression 0` | **2.92-3.00 s** | 0.11 s | 26 ms |
| `core.looseCompression 1` | 8.77 s | 0.11 s | 24 ms |
| `update-index --info-only` (no objects) | 0.93 s | -- | -- |
| 4 parallel `hash-object -w` + info-only | 1.90 s | fails on symlinked dirs | -- |

`--info-only` is fastest and builds a repository whose blobs do not exist: `git
diff HEAD` on any file a run modifies would die with "unable to read". Not
worth 2 s.

## 4. Decisions

**`where = "remote"` for both jobs.** Remote wins every variant under the Mac's
real load, and at load ~6 warm `check` is a tie. `auto` would have to find a
load at which local is clearly better, and there is none in these numbers. It
would also ask the wrong question: the pressure gate `auto` is defined against
(`pandora/client/pressure.py`) opens at 5 % free memory or a load of 8 per core
-- 80 on this Mac -- which is a thrashing machine, not a busy one. At load 60,
with 11 GiB of swap, it said "fine" all afternoon. So `auto` today would route
native-unit *locally* in exactly the conditions where it took 3.6× longer.

**Proposed eichler change (not made).** `tools/validation/plan.mjs` line 35:

```js
-    pnpm('exec', 'turbo', 'run', 'typecheck', '--concurrency=2'),
+    pnpm('exec', 'turbo', 'run', 'typecheck', `--concurrency=${process.env.PANDORA_CPUS || 2}`),
```

-16 % on a cold typecheck on the worker when it is alone (`PANDORA_CPUS=4`), and
unchanged when two runs share it (`PANDORA_CPUS=2`). The same one-word change to
`workers` in `validate.mjs` line 105 (`direct ? 2 : workers()` ->
`direct ? Number(process.env.PANDORA_CPUS) || 2 : workers()`) would raise jest's
`--maxWorkers` for `native-unit`; not measured.

## 5. Three bugs the measurements found, all fixed

**A fresh worktree could not run `pnpm check` on the worker** (`8dbdac9`). Same
bytes, new mtimes: `rsync -a` gave every injected file a date after the golden's
install, and pnpm's verify-deps-before-run -- which judges patches by mtime
alone -- refused with `Patches were modified` in 0.7 s. Journeys never saw it:
they call `node`. Injection is now `rsync -a --no-times --checksum`: unchanged
files keep the golden's mtime, changed ones get now. 0.53 s against 0.12 s.

**The shim ran a command locally that the daemon then also ran remotely**
(`5585077`). Freezing the fresh worktree took 21 s (its files out of the page
cache, 11 GiB of swap). The shim's 20 s handshake timeout read that as a dead
daemon and fell back -- while the daemon finished and submitted. Twice; both
remote runs executed with nobody attached (`r50f4e9648be4420`,
`r8f7714e2576f49d`). The local half failed only because that worktree had no
`node_modules`. The daemon now sends a `working` frame every 5 s before
`accepted`, so the timeout measures silence, not work; and a caller found gone
when the submission returns gets the remote run cancelled and the row closed
`withdrawn`. After the fix the same edit variant waited 25.7 s pre-accept and
ran once, remotely.

**The freeze read the worktree twice, every time** (`911f3e2`). 6 s page-cached,
10.9-21 s not. A stat-keyed digest table per worktree under the daemon's state
(git's index idea; a file touched within 2 s of the read is always re-hashed)
brings it to 1.7-2.0 s and a warm remote `check` from 24.3 s to 20.3 s.

## 6. The subdirectory rule (owner decision), done

`6487e07`. A claimed command typed below the worktree root with an argument that
names a path (a `/`, or a token that exists where it was typed) is refused:

    ~/eichler-wt/journey-runner-proxy/apps/agent$ pnpm test:native-unit src/nothing.test.ts

by the daemon, and by the shim from the enrolment marker when the daemon is
gone. Nothing runs anywhere. An argv naming no path is still re-rooted.
`[matching] subdirectory = "local"` is renamed `"reroot"`; the old word loads.

## 7. Recommendations

1. Take the `plan.mjs` line above into the eichler PR.
2. Re-tune `[local.pause]` before anything uses it to *route*: a load threshold
   near 2 per core (20 here) and swap growth, not 8 per core.
3. The synthetic git is now the largest fixed cost of a warm remote `check`
   (3.1 s of 20). If it matters: build the index with `--info-only` and write
   blobs lazily, or cache a per-input `.git` on the host keyed by `input_id`.
4. The source cache on the worker grew from 1.2 to 2.3 GiB in one afternoon of
   two worktrees -- `--link-dest` dedups only on equal mtime, which a fresh
   worktree never has. Content-addressed dedup (the freeze already has every
   sha256) is the fix; until then `pandora worker gc` needs a source-cache rule.
5. `test_shards.FanoutTest.test_two_shards_writing_one_path_differently_exit_75_and_keep_both`
   fails about one run in four on this loaded Mac, on `2912f61` as well as after
   this work. Pre-existing and timing-dependent.
