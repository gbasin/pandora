# `--update` write-back, 2026-09-22

Branch `v0.2/writeback`, from `v0.2/assembly` at `7484bb8`. Item 4 of "What
remains" in `notes/v0.2-slice-2026-09-22.md`: a `--update` run now executes on
the worker, and the files it rewrites come home under the rules below. The
refusal that told agents to use `PANDORA_OFF=1` is gone.

**No live worker run happened in this work.** Every result here is a unit test
against the existing fakes (`WritingDriver`, a fake `Worker`, a real daemon on a
real socket, real git worktrees frozen for real). Nothing was run on
`ubuntu@WORKER`, and no daemon was started against real state on this Mac.

458 tests, `python3 -m unittest discover -s pandora`, ~50 s, green (417 before).

## Behaviour

A write-back is **one publication: every file or none**. Each file is written
by temporary file in the same directory, `fsync`, then `os.replace`; the mode of
the file it replaces is kept. The set is not a transaction: a crash between two
renames leaves the earlier ones written.

| Case | What is written | Exit | What the caller sees |
|---|---|---|---|
| run passed; every declared file it changed is still as frozen here | the worker's version of each changed file | 0 | `pandora: wrote back N file(s): ...`, then `pandora: hint: review \`git diff\` of N updated files, then validate without --update` |
| run passed; changed nothing declared | nothing | 0 | `the run changed none of the declared files` |
| a declared file the run changed was **edited here** during the run | nothing, not even the other files | 75 | each path with `(the worker's: <state>/runs/<id>/writeback/<path>)`, then `pandora resolve <id> --keep-local` / `--take-worker`; the hint repeats it |
| a declared file **absent at freeze**, created by the run, and absent here | the new file | 0 | as the first row |
| the same, but a file now exists here at that path | nothing | 75 | as a conflict: the frozen hash is "absent", and a local file is a local edit |
| a declared file **present at freeze** and **absent after the run** | nothing | 70 | `not written back: ... Write-back never deletes` |
| a local file already byte-equal to the proposal | skipped for that file | 0 | not a conflict |
| **stale**: any file outside the declared files and declared artifacts differs from the submitted manifest | nothing | 75 | `not written back: the worktree changed outside the declared files during the run: src/x.ts. The proposal is kept in ...`; hint says re-run with `--update` |
| worktree cannot be re-frozen (it moved while being read, a symlink out) | nothing | 75 | treated as stale, with the freeze's reason in place of a path |
| **shard failed** (or never dispatched, or no report, or partition unverified) | nothing from any shard | the command's own non-zero (or 70 for an engine verdict) | `not written back: shard 2 did not pass, so no shard's files were written back` |
| two shards changed one declared file differently | nothing | 75 | `not written back: 1 declared file(s) were changed differently by more than one shard` |
| two shards changed **disjoint top-level keys** of one JSON object | the merged file | 0 | as the first row |
| run failed, oom, timed out, cancelled | nothing | the run's own | `not written back: the run did not pass` |
| proposed bytes arrive with the wrong sha256, or the fetch fails | nothing | 70 | the paths |
| infrastructure failure **before** `accepted` | nothing, and nothing runs here | 70 | `fallback-refused: ... a write-back run is never run locally` |
| infrastructure failure **after** `accepted` | nothing | 70 | `lost the worker while run ... was executing` |
| `where = "local"` job | unchanged: config validation refuses `writeback` outputs on a local job; a local run writes in place | | |

### Paths

Declared paths are resolved against the **worktree root**, not the directory
the command was typed in (a re-rooted run gets the same paths as a root one; the
same fix now applies to artifacts, which were being rooted at `cwd`).

* A literal path names one file, or every regular file below it when it is a
  directory. Directories are expanded per file; there is no whole-directory
  replacement, because write-back never deletes, and a directory replacement
  is a delete of whatever the new generation lacks.
* A glob may appear only in the last component and matches regular files
  directly inside that one directory (`fnmatchcase`). `fixtures/*.ledger.jsonl`
  loads; `*.json`, `fix*/routes.json` and `fixtures/**/x.json` are refused at
  load time.
* Symlinks are neither followed nor written. A declared path under a symlinked
  directory, or resolving outside the worktree, is a conflict -- or stale, when
  the re-freeze itself refuses the symlink first. Either way nothing is written.

### Stale, and why it is the whole tree

The run's proposal is a function of its whole input. An edit to `src/x.ts` while
the run was away means the fixtures describe code that no longer exists, so the
rule is v0.1.1's `source_is_current`: the worktree is frozen again after the
run (with the daemon's `digests` cache, so mostly stats) and compared record by
record with the submitted manifest, **ignoring the declared write-back files
and the declared artifact paths** -- the former are the conflict check's job,
the latter are written into the worktree by `deliver` a moment earlier. This
applies whatever the job's `drift` setting says: `drift` is a local-lane key
about verdicts, and a write-back is not a verdict.

### Resolve

`pandora resolve <id> --keep-local` records that the declared files as they are
now are the answer -- the agent merged the worker's versions by hand, or chose
its own -- writes nothing, and says the result was not validated.
`--take-worker` publishes the whole proposal, but only over files still exactly
as the conflict report saw them; a file edited again after the report makes it
exit 75 and write nothing. Both work without the daemon or the worker. Only a
`conflicted` write-back can be resolved; a stale one is re-run.

The v0.1.1 name was `pandora resolve-expectations <id> --keep-local`. The verb
is `resolve` now because write-back is not only expectations, and `--take-worker`
is new. Unlike v0.1.1, a conflicted run does **not** block the next validation in
the worktree: v0.2 has no active-request lock for remote runs to hold, so
resolving is bookkeeping plus the one write `--take-worker` makes.

## Configuration

No key changed shape. **eichler's `pandora.toml` needs no edit** for this: its
journey job's `options` and `outputs` already declare exactly what is used. One
rule is new: a `writeback` path may glob only its last component, below a
directory (`_writeback_path`). Eichler's two paths comply.

| Key | Meaning now |
|---|---|
| `options = [{ name, sets, forward, writeback = true }]` | arms the job's `writeback` outputs when typed; `forward = true` passes it to the runner |
| `outputs = [{ kind = "writeback", requires_option, paths }]` | declared files the armed run may rewrite; `requires_option` must name a `writeback = true` option |
| `where = "local"` + `writeback` | still refused at load |

`journey-runner.mjs` needs nothing new: it must exit 0 only when the update
succeeded, and write the files at their worktree paths inside the instance.

## Fallback: already encoded, now pinned

`fallback.decide(writeback=True)` refuses before any other rule, and
`daemon.fall_back` passes `plan['options']['update'] or plan['writeback']`.
Before this work the pre-accept refusal in `serve_run` returned before
`fall_back` was reachable, so `test_a_write_back_run_never_falls_back` was
passing through the refusal rather than the policy. It now passes through the
policy. New tests pin a `small` job -- which would otherwise earn the local lane
-- refused with 70 both before `accepted` (`fallback-refused`) and after it (the
follow loop's infrastructure failure), with the job's marker file absent, and
the same job without `--update` still falling back.

## Found in the existing code

* **Remote runs have no drift check.** The brief for this work, and
  `docs/agents-paragraphs.md` ("Exit 75 means ... the source changed during the
  run"), say a source change during a remote run makes it stale. In
  `v0.2/assembly` only the local lane (`client/local.py`) re-freezes; a remote
  verdict is never checked against the tree afterwards. Write-back now does its
  own check, as above. Ordinary remote runs still do not.
* **There is no catalog job.** `eichler.pandora.toml` claims `journey` only;
  `pnpm journeys` is not routed in v0.2, so "partial suites do not update" is
  implemented and tested against the generic fan-out (`surface`-shaped shards)
  and has no eichler job to apply to yet.
* **Re-rooted remote runs delivered artifacts under the subdirectory.**
  `deliver` rooted `collect` at `run.request['cwd']`. Fixed in `507a03a`; the
  run now carries its worktree and `meta.json` records it.
* **The enrolment marker's `writeback` flag is per job, not per option.** With
  the daemon down, `pnpm journey S0-01` without `--update` is refused as a
  write-back run. Harmless for `journey` (it declares `fallback = "refuse"`
  anyway); overly strict for a `small` job that declares write-back outputs.

## What is unverified

* **Everything against a real worker.** `incus file pull -r` of a directory
  into a parent, the `sudo chown` after it, and `rsync` of
  `runs/<id>/writeback/` back to the Mac are exercised only through fakes.
* **Eichler's runner and its file format.** The JSON merge reproduces a file
  only when every shard's output and the frozen base round-trip through one of
  twelve `json.dumps` styles (indent 2/4/none, sorted or not, trailing newline
  or not). v0.1.1 wrote `write-routes.json` as sorted keys, indent 2, trailing
  newline, which is one of them; whether eichler's current runner still does is
  not checked.
* **What v0.1.1 checked and this does not.** v0.1.1 required the runner's own
  report (`results/journey.json` with `update: true` and `status: pass`), and
  refused a focused update that changed another journey's route entry. v0.2
  trusts exit 0 and publishes whatever declared files changed.
* **Crash recovery mid-publication.** v0.1.1 kept an intent file and resumed.
  Here a daemon killed between two renames leaves those written, the record not
  saved, and the run adopted as `running`; re-attach re-settles, and each
  already-written file is then "equal to the proposal" and skipped. Reasoned,
  not tested.
* **Cost.** `writeback.json` holds the whole manifest minus declared paths,
  ~4,900 records for eichler, per `--update` run, under retention's normal
  window. The post-run re-freeze is the same freeze `submit` does, with the same
  digest cache; not measured.
